- **An entry point configures logging in its `main()`; an imported module never does** (#442). `src/scraper/amazon/scraper.py` called `setup_debug_logging` at module scope to catch errors raised while Botasaurus loads, and `ProductData` is imported from that module by the producer, the publisher, the batch and `tests/conftest.py` -- so every one of those processes had its **root** logger pointed at the production `outputs/logs/scraper.log` before its own `main()` ran. Measured on one full test run: 430 KB of pytest output appended to real scrape history, the rotation chain rolled, and the oldest copy destroyed. It also made two downstream fixes inert, because `logging.basicConfig` is a documented no-op once root has handlers: the producer CLI's config-failure fallback (now `force=True`) and the test suite's autouse fixture, which configured nothing at all and hid the leak it looked like it was preventing. The fixture now restores root's handlers and level after each test instead, and a second one neutralises `setup_debug_logging` so a test driving an entry point writes nothing -- **bound to the real signature**, because the obvious variadic stand-in swallows a renamed keyword and those `main()`-driving tests are the only coverage that call site has: a mutation that killed every real scrape left the suite green. It patches only modules `sys.modules` already holds; anything imported later binds the stand-in off the patched source module, and resolving all five eagerly pulls the scraper, publisher and producer stacks into every session, which costs a targeted single-file run seconds. The cost accepted is the window before `main()`: a record raised while the module tree loads reaches logging's last-resort handler on stderr rather than the file. `tests/utils/test_logging_appends.py` guards both halves -- an AST check that no module-level call comes back, and a subprocess that imports the module in a fresh interpreter and asserts root has no handlers and the production log is byte-identical afterwards. In-process re-import proves nothing there; the module is already in `sys.modules`.
- **A config that does not load is a stop, and three layers used to disagree** (#455). `ModularConfigAdapter._load_yaml_file` logged a parse error and returned `{}`, `get_video_config` answered any exception with a hardcoded dict rendering 1920x1080 at 30fps with Arial 48 subtitles, and `get_scraper_config` did the same for every exception but two. A typo in a YAML file therefore changed the output format instead of failing the run, and those hardcoded dicts were a second declaration of defaults the models already own -- the source of the `sort_order` and `remove_temp_on_success` duplicates. All three now propagate; a **missing** file is still a warning, because the five files are optional layers. `UnifiedConfigManager` itself stays: it is the merge and CLI/env precedence engine that both `load_video_config_modular` and `load_scraper_config_modular` call, not a third system, whatever #455's original framing said. `get_config_value` is gone with it, and the readers use the typed models. **`system_timeouts` was the catch**: `config/core.yaml` carries that block and the video config merges it, but `VideoConfig` never declared it (`extra` is not forbidden there, so it validated in silence), so the dotted reader was the only thing that could see it -- and the value it returned happened to equal the call site's own default, which is what made the knob look dead. It is a declared field now. An undeclared key in a merged YAML file is reachable only by an unchecked reader, so removing the reader silently removes the setting.
- **The scraper's configuration is typed; readers carry no defaults of their own** (#125). `ScraperConfig` in `src/scraper/config_models.py` is the one place a default lives, every submodel is `extra="forbid"`, and all three loaders -- `ScraperConfigAdapter._merge_scraper_configs`, `PlatformConfigManager._load_config` and `BotasaurusAmazonScraper._load_config` -- validate through `ScraperConfig.from_legacy_dict` and hand out `to_runtime_dict()`, the defaults-filled dict in the file's own shape (`scrapers.amazon`, top-level `batch`). Consumers read `get_settings()` from `src/scraper/amazon/config.py`, a function rather than the module attribute because `SETTINGS` is rebound at load and a name imported earlier keeps the defaults. A misspelled key raises `ValidationError` at import of `src/scraper/amazon/config.py`, which is any path that reads scraper config; the generic except that used to install a hand-written fallback dict re-raises it. It is no longer raised by a bare `import src.scraper.amazon`, since the package stopped re-exporting eagerly (#470), so a producer-only run does not validate the scraper's YAML. **A test that builds a scraper with `__new__` must set `scraper.settings`**, and one that simulated the file by patching `CONFIG` patches `SETTINGS` with `ScraperConfig.from_legacy_dict(...)` instead. `tests/scraper/test_typed_scraper_config.py` greps for a numeric fallback on any config-shaped receiver; reads of result data (`stats.get("total_images", 0)`) are not that bug and are left alone, which is why the issue's plain regex still finds eleven. The models existed from 0.7x with `load_scraper_config_pydantic` as their only constructor, which nothing called: the fourth-condition class, a model nobody reads.
- **The scraper's command line is `src/scraper/amazon/cli.py`; `scraper.py` holds the class and re-exports `main` so `python -m src.scraper.amazon.scraper` keeps working** (#456). A test that reads the entry point's source -- the logging AST guards, the chunk-argument check, the rotation-sharing check -- reads `cli.py`, and `tests/conftest.py` neutralises `setup_debug_logging` there. **The trap in the move was `global DEBUG_MODE`**: it bound the flag in whichever module `main` lived in, so moving the function silently left a config-driven debug run (`global_settings.debug_mode: true`, no `--debug`) with an invisible browser -- the CLI now sets `scraper_module.DEBUG_MODE` explicitly. The scraper no longer imports anything from `src.video`: `--profile NAME` resolved a whole video config for one boolean and is replaced by `--profile-uses-videos` / `--no-profile-uses-videos`, which the batch computes for itself.
- **URL support**: Scraper accepts full URLs (including shortened URLs like tr.ee) via `--product-ids` or `--input-file`. URLs are detected by `startswith("http")`, navigated directly in the browser, and ASIN is extracted from the redirected URL via regex `/dp/([A-Z0-9]{10})`.
- **CLI args**: `--input-file FILE` (one URL/ASIN per line), `--batch-size N` (process in chunks), `--output-dir DIR` (override output directory).
- **Botasaurus output dir override**: Botasaurus framework callbacks don't accept custom parameters. Use module-level `set_output_dir()` in `botasaurus_output.py` before running the scraper. The `_effective_dir()` helper resolves: explicit param > module override > None (config default).
- **Variable initialization in browser_functions.py**: Variables used after `if is_url / elif is_asin / else` branching (like `count_products_with_media`, `products_with_media_count`, `max_products`) must be initialized **before** the branch, not inside one branch. Same trap for imports: a local `import X` inside a conditional branch makes `X` function-local for the **whole** function, so any path that skips the branch hits an unbound local when it touches `X` (a redundant `import time` inside `if DEBUG_MODE:` did exactly this and crashed every non-debug keyword scrape). Keep imports at module level. The function runs behind a Botasaurus `@browser` wrapper so unit tests mock it out; drive it with a mock `Driver` (see `tests/scraper/test_browser_scrape_impl.py`) to actually execute the body.
- **Two scraping code paths**: The standalone scraper CLI uses `scrape_products_unified()` which has a cycling loop (`_scrape_until_validated_count_reached`). The global batch uses `scrape_batch_browser()` + `process_raw_products()` with its own page retry loop in `src/pipeline/phases/scraping.py`. Changes to validation logic must be tested through both paths.
- **Amazon's error page means two different things, and the run tells them apart from its other inputs.** `Sorry! Something went wrong!` is returned both by a rate limit, which clears in minutes, and by a query that never works, which never clears. They want opposite responses and the message is identical, so the old handling was wrong for both: a fixed tenacity policy of three attempts at most ten seconds apart, which landed inside a block measured clearing after several minutes, and which no wait could have helped on a dead query. `src/scraper/base/throttle.py` owns the decision. The evidence is that a rate limit blocks the connection, so nothing else gets through either: an input that keeps failing in a run where *some other* input succeeded is a dead query and is skipped; one that fails with nothing else succeeding is throttled and is waited on, doubling from `throttle_backoff_base_sec` to `throttle_backoff_max_sec`. **The evidence is deliberately not ordered.** Requiring the other success to come after the failure reads better, but a dead query is as likely to be the last input in a run as any other, and nothing succeeds after the last input by definition -- that version left exactly that input un-rulable and spending its whole budget. `dead_query_after` (3) is the guard instead: two backoffs, several minutes, have elapsed before anything is called dead. The residual misread is a rate limit that begins partway through a run after something has already succeeded: **every** later input is named dead, not only the first, so the summary is wrong about why most of the run failed though not about which inputs were lost. `dead_queries` and `throttled_inputs` must not overlap -- an input ruled dead reached the throttled list through its own earlier RETRY verdicts, and reporting it under both headings tells the operator to replace a keyword and, in the next line, that the same keyword only needed a longer gap. **The error-page check has to be unconditional**: both checks used to sit inside `if DEBUG_MODE:` and the bundled config ships debug off, so on a normal run the page produced an empty result and no exception, which the batch loop recorded as a *success* -- turning a throttled input into evidence that the connection works. One was also in the keyword branch alone, so an ASIN or URL scrape never reached it even with `--debug`; `raise_if_error_page` now runs after every navigation in every arm, and outside the keyword arm's navigation handler, which catches everything and returns an empty list. **The ceiling is only reachable if `throttle_max_attempts` is high enough** -- at 5 the longest wait taken was 480s and raising `throttle_backoff_max_sec` changed nothing, which made the documented remedy a no-op. Waiting is also capped for the run as a whole, since per-input budgets do not compose. **Both scraping paths feed one tracker**, held on the scraper instance so it is one per run: sharing one across runs would let an earlier run's successes rule a later run's first failure a dead query. The standalone path needs the exception to survive **two** swallows above the impl: `create_dynamic_browser_function`'s wrapper, which catches everything and returns an empty list, and Botasaurus's `@browser` decorator itself, which catches everything the decorated function raises, re-runs the whole task `max_retry` times (three on the normal config, one under `--debug`) and returns `None`. Re-raising inside the function reaches nothing — the caller sees no exception, records the throttled input as a *success*, and pays for those extra Chrome launches into a live block. `AmazonErrorPageError` exists so `must_raise_exceptions` can name it; the decorator matches by class, not by message, so a site that raises a bare `RuntimeError` with the right text is still swallowed, and `is_error_page_failure` (which matches the message) will not save it. A test that patches the decorator with a pass-through asserts the opposite of production and is worthless here — drive the real decorator, replacing `botasaurus.browser_decorator.Driver`. `create_driver` is accepted by the decorator's signature and never called, so setting it launches real Chrome and leaves screenshots in `error_logs/`; the stub also needs a `config` object, since the decorator writes `driver.config.is_last_retry` before each attempt. **`throttled_inputs` reads the input's most recent outcome; `dead_queries` requires that it never succeeded.** The batch's page-retry loop reuses one tracker, so a keyword that delivered on page one and was blocked from page two onward has to appear in the throttled list -- filtering both on ever-succeeded lost it -- while filtering `dead_queries` on the recent outcome would call that same keyword dead. **The verdict has to apply the same exclusion as the list it feeds**: `record_error_page` once asked only whether another input got through, so it skipped a keyword the summary was simultaneously calling rate-limited, and at `dead_query_after: 1` put it in neither list. **An empty result is not evidence that the connection works** -- both the impl's navigation handler and the browser wrapper return one for a swallowed failure -- so `record_success` is called only for a result carrying products. `summary_lines_for` is the single wording, because three hand-rolled copies had already drifted. **`throttled_inputs` is a summary list, not the give-up signal** -- an input joins it on its first `RETRY`, so a caller reading it to decide whether to stop trying ends the input with its whole budget unspent; the gate reads `dead_queries` or `exhausted_inputs`. `scrape_batch_items` is split out of the Botasaurus `@browser` wrapper so the loop can be driven with a fake driver -- anything left inside that wrapper is only ever exercised against Amazon. Mocks of the scraper must carry a real `ThrottleTracker`: the summary joins its verdict lists, and a bare `Mock` raises `TypeError: can only join an iterable`.
- **Page retry**: both entry points retry with additional search pages when products fail media validation, and both gate it on the input mode: keyword searches only, never ASINs or URLs. A URL names one product, so every later page re-resolves the same listing. The two paths read different knobs: the batch is bounded by `max_retry_pages` (`config/scraper.yaml`, default 5), the standalone loop by `max_pages` (code default 7, honoured from `global_settings.batch_processing.max_pages` when set but absent from the bundled file). It also reads `max_scrape_attempts` (`config/scraper.yaml`, 50), but that counter only advances on a page that yielded validated products, so on a listing that never validates it stays at 0 and `max_pages` is the only stop. The batch gates in `_execute_scraping_phase` (`is_keyword`); the standalone scraper gates in `scrape_products_unified` before it reaches `_scrape_until_validated_count_reached`. That second gate was missing until 0.93.1, so a media-poor URL was re-fetched for all seven pages before the loop gave up and returned empty. The run continued to the next input, so nothing was dropped; the cost was the wasted sessions.
- **Price/rating extraction in `product_extractor.py`**: `_normalize_price` infers the decimal separator from the value, so it handles both US (`$1,234.56`) and EU (`1.234,56`) formats; a lone separator followed by exactly 3 digits is treated as thousands grouping, not a decimal. Price selectors are scoped to the core price block and skip `.a-text-price` so the struck-through list price isn't read; when only `.a-price-whole`/`.a-price-fraction` are present, `_price_from_parts` reconstructs cents instead of truncating to whole dollars. Rating and review count come from the detail page on every arm (`_extract_detail_rating` / `_extract_detail_reviews_count`), with the search card as the fallback: `ProductData.__post_init__` fills `rating` from `serp_rating` only when the page's star widget could not be read, so the guard is load-bearing rather than dead. They used to come from the card alone, so a scrape by ASIN or URL -- which never sees one -- produced a record with no rating; `reviews_count` was never persisted on any arm, since only `rating` has a fallback. The specific review hooks are tried before `.a-icon-alt`, which matches every star widget on the page including a single customer review's, and a candidate that is not a number is rejected -- a truthy wrong rating would also suppress the card fallback. `to_dict()` must emit `rating` (it was dropped from the scraper's old serialiser once, so the fallback never reached `data.json`).
- **A selector loop must break on the text, not on the element.** The detail page carries `productTitle` twice: the `<span id="productTitle">` that holds the title, and a hidden `<input name="productTitle" id="productTitle">` whose *value* is the title and whose text is empty. The id is duplicated, so which one `select("#productTitle")` returns is a property of the page, not of this code. Breaking on the element being present meant the empty input ended the chain and `h1.a-size-large`, `.product-title` and the automation-id hook were never tried, any of which would have worked. Cost: a batch ran 51 minutes over two keywords and validated **zero of 27 products**, each dropped as titleless with price, rating and description intact, because `is_valid_product_data` reduces to a title check under the shipped `essential_fields: []`. Nothing about the run looked like a failure -- products attempted, none valid, which reads as ordinary media attrition -- and the one WARNING that explains a rejection passed `"" if description else ""` for two of its fields, so it printed `description=` and `rating=` whichever way those went and named no cause. The description loop had the same shape. An AST test now fails if either loop's guard stops reaching `.text`, because a behavioural test that re-implements the loop keeps passing after the real one regresses; it finds each loop by the selector list it walks rather than counting text-guards in the module, since a count is restored by tidying any unrelated loop into the same shape while this one regresses. **Falling through also made a page-wide selector reachable that previously could not be hit**: the description chain ended at `.a-unordered-list.a-vertical`, unscoped, so an empty feature-bullet block would have put the first vertical list on the page -- nav, customer questions, a footer -- into the narration. It is scoped to `#feature-bullets` now. Widening what a fallback chain can reach is the cost of fixing one that stopped too early, and the last entry in a chain is where it lands.
- **Standalone CLI must load `.env` at startup**: `src/scraper/amazon/scraper.py::main()` calls `load_dotenv()` before parsing args. Without it, env-only secrets like `AMAZON_ASSOCIATE_TAG` are invisible to `build_affiliate_url`, which silently falls back to returning the input URL unchanged. The global batch entry point in `src/pipeline/cli.py::main()` does the same. Any new CLI entry point that reads env vars needs the same call.
- **`build_affiliate_url` logs WARNING on missing associate tag**: in `src/scraper/amazon/utils.py`. The fallback (return input URL unchanged) is preserved for backward compatibility, but the warning makes the silent-revenue-loss class of bug grep-able in `outputs/logs/scraper-<date>.log`. Future work to harden this is tracked as a GitHub issue with the `follow-up` label.
- **`scrapers.amazon.affiliate_links.enabled: false` means "no program", not "misconfigured"**: the missing-tag WARNING exists to catch a mistake, so an install with no affiliate account got a revenue-loss warning per product plus URLs carrying whatever tracking params the SERP happened to attach. With the flag off, `build_affiliate_url` strips to a bare `https://www.amazon.com/dp/<ASIN>` and logs at DEBUG. The flag governs the missing-tag path only: an explicit `associate_tag` or `AMAZON_ASSOCIATE_TAG` still wins, so it can't silently discard a working program. Read via `_affiliate_links_enabled()`, which checks `AMAZON_AFFILIATE_LINKS_ENABLED` first (a blank value falls through, so `FOO=` doesn't read as false) and defaults to enabled (a missing/unreadable config must not silence the warning).
- **URL shortener default is `bare` (no-op)**: bundled `config/url_shortener.yaml` ships `provider: bare`. Picsee is opt-in via `provider: picsee` + `PICSEE_API_KEY`. The `_shorten_affiliate_links` function bypasses the API-key gate for the bare provider. It reads `self.url_shortener_settings`, a `URLShortenerSettings` loaded in the scraper's constructor by `load_url_shortener_settings` (`src/utils/url_shortener/config.py`), which **mirrors the YAML field for field** -- `api.timeout_sec`, `picsee.custom_domain`, `integration.shorten_on_scrape`. The model used to be a flattened paraphrase that nothing populated while the consumer walked the YAML dict with its own defaults, so the two default sets drifted and a typo'd key fell through to a default. `extra="forbid"` on every block now reports a typo at load, and providers are **declared fields** (`bare`, `picsee`) rather than collected from unknown keys, so a misspelled provider section fails instead of silently configuring nothing. Adding a provider means adding a field, and its defaults match what the old dict-walk read an absent key as (`enabled` and `shorten_on_scrape` off, `api_key_env_var` defaulting to the name `PICSEE_API_KEY`), so a partial override file behaves as before. **The models deliberately do not live in `src/video/config/`**: that package's `config` singleton resolves lazily now, so importing a submodule is safe, but *resolving* it still loads the whole video config from five cwd-relative YAML files -- so a scraper that touched it from another directory, or on a box with an unrelated video-config error, would still fail. The placement stands; only the import-time half of the hazard is gone. The default config path is anchored on `__file__` for the same reason.
- **Headful Chrome on Wayland needs an X display, and a *visible* one freezes CDP**: the scraper forces `--ozone-platform=x11` (in `_build_browser_config`) so Chrome draws on an X server, not a real Wayland window. Normal runs use Botasaurus's Xvfb (`enable_xvfb_virtual_display=True`). Unsetting `WAYLAND_DISPLAY` alone is not enough — libwayland defaults to the `wayland-0` socket, so the explicit ozone flag is required. A real on-screen window on a live Wayland session makes Chromium's CDP endpoint go unresponsive (`Failed to connect to Chrome URL`, then per-navigation `Response not received` ~400s hangs), so debug runs on Wayland route to Xvfb too (guarded on `WAYLAND_DISPLAY` in the `force_real_browser` branch) and are invisible. To watch a debug scrape, `make scrape-watch` runs it on a dedicated Xvfb + `x11vnc` (VNC at `localhost:5900`). `x11vnc` refuses to start on a detected Wayland session, so the target launches it with `WAYLAND_DISPLAY`/`XDG_SESSION_TYPE` truly unset (`env -u`) — an empty value isn't enough for `getenv`. The browser launch profile and navigation timing are logged at DEBUG to triage display/CDP issues from `outputs/logs/scraper-<date>.log` alone.
- **NO_PROXY CIDR caveat for Chrome CDP**: Botasaurus connects to Chrome's DevTools endpoint at `127.0.0.1` via Python's `urllib`. Python's proxy bypass check does not parse CIDR notation (`127.0.0.0/8`), so if a system proxy is configured, `127.0.0.1` requests get routed through the proxy and fail with `502 Bad Gateway` or timeout. The fix (in `browser_functions.py` at module import) adds the exact `127.0.0.1` to `NO_PROXY`. The same issue affects the Zernio SDK (httpx), which also reads proxy env vars — if `ALL_PROXY` is set to a `socks://` URL, httpx raises `ValueError: Unknown scheme for proxy URL`. Workaround: unset `ALL_PROXY` / `all_proxy` before running the publisher.
- **Vercel security checkpoint through proxies**: Requests to Zernio API through an HTTP proxy can hit a Vercel WAF challenge (HTTP 403 with `X-Vercel-Mitigated: challenge`). Retrying after a brief pause usually succeeds, as the challenge is per-request, not per-IP. The no-proxy path avoids the challenge but is significantly slower on some networks.
- **TikTok account restrictions are not retryable**: `This TikTok account has been restricted from posting. Please check your TikTok account status.` is a TikTok-side account restriction. Retrying via Zernio `posts.retry()` produces the same error. The account must be resolved in TikTok's app or support.
- **The host's `WAYLAND_DISPLAY` leaks into the browser-config tests.** `_build_browser_config` reads it from the environment, so on a Wayland desktop the test for the no-display branch took the Wayland branch instead and passed on a message that merely contained the word `display`; on CI (no Wayland) it tested what it named. A test of one branch of that function clears the variable (`monkeypatch.delenv("WAYLAND_DISPLAY", raising=False)`) or sets it, never inherits it.
