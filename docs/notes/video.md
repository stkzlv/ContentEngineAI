- **Profile settings**: `get_profile_merged_settings()` returns typed `MergedProfileSettings` (not dicts). Access via `.video_settings.field` and `.subtitle_settings.field`. Use `.model_dump()` when downstream functions need dicts.
- **The static upper line is an assembler overlay, not a subtitle feature, and that is the whole point** (`video_settings.upper_line`, #88). Two-part mode renders a line above the visual, but `step_generate_subtitles` disables two-part when the engine is pycaps, so a profile that switched engines lost it with one debug line; pycaps has a single caption track and no static element to carry it. The line is static for the whole video, so it needs no engine: `apply_upper_line_overlay` rewrites the chain's terminal the way the disclosure does, which puts it in the assembler output that the pycaps burn *composes over* and that the FFmpeg caption fallback runs after -- the fallback being exactly when a subtitle-side implementation would lose it. A line it actually draws forces `two_part_subtitles.upper_line.enabled = False`, or FFmpeg draws the same text twice -- **the condition is the drawn line, not the flag**: superseding on `enabled` alone switched two-part off on a render the overlay then declined, losing both. **The resolver returns a reason, not just a value**: `affiliate_link` on a topic and `link_in_bio` with no `LINK_IN_BIO_URL` are ordinary outcomes, and an unresolved source must draw nothing rather than a bare background box. The bio URL is read from the environment because the public config carries no account-specific value and the link-in-bio module holds OAuth credentials rather than a public URL; `SUBTITLE_BUSINESS_URL` is read as a fallback, since the two-part upper line has taken the same value from it since it shipped and six bundled profiles point at it -- a second variable for one value would have silently lost the line for an installation that already had it working. The image band reserves the line's rows (`upper_line_bottom`) in **both** `visual_builder` and `two_part_subtitles._image_band`, or the pre-assembly caption estimate is computed against a band the image no longer occupies. `upper_line` is on `VideoProfile` as a `PartialUpperLine` merged at its own call site rather than through `_collect_overrides`, which replaces whole fields and would reset every styling field a profile did not restate; `tests/video/test_profile_override_coverage.py` exempts it only on condition that it reads the merge, since an exemption with nothing behind it is the silent drop that file exists to catch.
- **Disclosure overlay is the LAST video filter**: `apply_disclosure_overlay` in `src/video/assembler/overlay_builder.py` rewrites the subtitle builder's terminal `copy[v_out]` no-op into a drawtext that produces `[v_out]` directly. Chains that end some other way are normalized first by `_ensure_copy_terminal`, which re-points the terminal filter at `[v_pre_overlay]` and appends the missing no-op — that is what lets both overlays apply on the content-aware ASS path, which ends with `ass='...'[v_out]` and used to drop them silently. The remaining unrecoverable shape is a terminal that doesn't produce `[v_out]` at all; that still logs a warning and skips, so `#ad` won't appear. Any new terminal filter shape in subtitle_builder should be checked against that helper. Pycaps overlays its captions on the assembler output, so the overlay survives the pycaps step automatically.
- **Drawtext has no font fallback chain, so every overlay resolves its own face** (#392): text in a script the default `Sans` face does not carry rendered as empty notdef boxes, silently, exit 0. `font_resolver.fontfile_for_text` asks fontconfig (`fc-list ':charset=...'`) for a face covering every non-ASCII glyph and the three overlay builders pass it as `fontfile=`; config validation refuses operator text (`disclosure_overlay.text`, `upper_line.custom_text`) nothing installed can draw, naming the glyphs, while render-time resolution degrades with a warning. `fc-list` with a charset returns only faces that genuinely cover it, which is what makes the empty answer a reliable loud-failure signal; `fc-match` always returns something and cannot be used for this.
- **FFmpeg filtergraph commas inside expressions need backslash-escaping, not quoting.** Phase 1.2c's hook overlay first shipped with `enable='between(t,0,X)'` per the FFmpeg docs' "quote to protect commas" rule. The filter failed at render with `Missing ')' or too many args in 'between(t'` because FFmpeg's parser still split at the inner commas when the filter sits inside a comma-separated chain (multiple drawtexts + the disclosure rewrite). The reliable form is `enable=between(t\,0\,X)` — backslash-escape the commas inside the expression. Same trick applies to any FFmpeg expression with embedded commas (`if`, `lt`, `gte`, `min`, `max`). The "wrap in single quotes" form is documented but unreliable in practice for filters embedded in larger chains. Verified with a synthetic `ffmpeg -vf "drawtext=...:enable=between(t\,0\,1.5)"` call.
- **Inline `text=` with an apostrophe corrupts inside a multi-filter chain; use `textfile=`.** The exit/reenter escape `'\''` (close-quote, backslash-quote, open-quote) survives a standalone `-vf` drawtext but NOT the assembler's multi-filter `-filter_complex` chain: when another filter follows, FFmpeg swallows the drawtext's own trailing args (`fontsize=`, `x=`, `enable=`) as literal text, rendering them as tiny garbage at the frame's top-left and dropping the intended text. Hit on the hook overlay for any hook whose first sentence had a contraction (`you're`, `it's`, `don't`); apostrophe-free hooks (the USB-C test case) hid it. Fix: write each line to a temp file and reference `textfile='<path>'` (colon-escape the path) — the same approach `subtitle_builder` already uses. `build_hook_drawtext` does this; `_escape_drawtext_text` is now only safe for the disclosure's config-controlled, apostrophe-free text (`#ad`/`#publi`). Alternative escapes tested: `'\''` mangles, `\\\'` drops the apostrophe, `textfile=` renders it verbatim. Verified by rendering the real `build_hook_drawtext` output through ffmpeg and viewing the frame. The disclosure overlay was later moved to `textfile=` too, since `disclosure_overlay.text` is user-configurable per language and a value like `Pub d'affiliation` would hit exactly this bug.
- **`textfile=` removes the quoting layer but NOT drawtext's text expansion — escape `%` and `\` in the file contents.** Both failures are silent and FFmpeg still exits 0: a raw `%` is read as the start of a `%{...}` function (logs `Stray %`, draws NOTHING for that line — the frame comes out byte-identical to one with no drawtext at all), and a raw `\` is swallowed (`a \ b` renders as `a  b`). Escape `\` -> `\\` first, then `%` -> `\%`, so the marker added for `%` survives. This bit the hook overlay immediately after the apostrophe fix above: switching from `text=` to `textfile=` dropped the `%` escaping that `_escape_drawtext_text` had been applying, and the hook headline prompt explicitly asks for price and percentage lines, so every percent-bearing hook silently vanished from the render. `_escape_drawtext_textfile` in `overlay_builder.py` is the single escaper for textfile contents; the older `_escape_drawtext_text` is for inline `text=` only. Lesson: when swapping how text reaches FFmpeg, re-check every metacharacter the old path handled, not just the one you set out to fix.
- **Disclosure config defaults are conservative on size, aggressive on margin**: 0.45 size_factor (slightly under FTC's 50-60% band) and 0.12 vertical margin (clears YouTube Shorts top header at ~10% and TikTok top username at 0-8%). Pydantic floors `size_factor` at 0.2; the runtime also floors the rendered fontsize at 8px so even a tiny subtitle base font doesn't produce illegible disclosures.
- **`BaseProductData.to_dict()` is the serialiser for everything that goes through `_save_products`.** The topic path calls it directly and the scraper's `_product_to_dict` now delegates to it, so a field added to the dataclass reaches the file on both, and `tests/scraper/test_data_json_serialiser.py` fails if a declared field stops being serialised. **It is not the only writer.** The Botasaurus `@browser` decorator calls `write_scraped_data_output` with the raw extractor dict (`browser_functions.py` `output=` -> `botasaurus_output.py`). All four scraper arms reach `_save_products`, so the raw dict is overwritten by the canonical serialiser: the global batch via `process_raw_products`, a standalone **single**-keyword run via `scrape_products`, a standalone **multi**-keyword run via `BatchController._process_keywords`, and a `--product-ids` run via `_process_product_ids`. The last two both used to leave the raw dict as the final file, so a product scraped by ASIN landed as the raw extractor dict, which lacked ten of `to_dict()`'s keys (`brand`, `category`, `pillar`, `platform_id`, `rating`, `reviews_count`, `search_position`, `shortened_affiliate_link`, `status`, `topic`) and carried an empty `downloaded_images` because the callback fires before the media downloads. `tests/scraper/test_data_json_serialiser.py` asserts the two standalone arms write the same key set. Check which arm produced the file your path makes before assuming a new field round-trips. It compares `to_dict()` against `dataclasses.fields()` rather than against a second dict, because two serialisers can agree with each other and both be missing a field — which is exactly how `pillar` used to persist for topics and vanish for scraped products. **The pillar has to be assigned before the write, not to the returned records** (#239). The three arms failed differently: the global batch assigned after the write, so its file said `pillar: null`; the standalone multi-keyword arm assigned to the record but never wrote through the serialiser, so its file had no `pillar` key at all; and the standalone single-keyword arm never assigned one, so its record and its file were both null. None of the three was caught, because the two that assigned at all left a correct record behind and the record is what tests looked at, which is why `tests/scraper/test_pillar_reaches_disk.py` asserts the file. `process_raw_products` takes a `pillar` argument, `scrape_products` resolves it per keyword through `pillar_for_keyword`, and the batch controller assigns then saves. On the global batch the returned objects are discarded outright: `_execute_handoff_phase` re-reads the directory. `to_dict()` routes both enums through `_enum_value`, since `ProductData(**loaded_json)` does no coercion and a record read back from disk carries plain strings where `.value` would raise.
- **The pipeline DAG and the step-to-function table are each declared once, in `orchestration.py`, and both execution paths read them.** `step_dependencies(profile)` is the graph; `step_runners()` maps every name in `VALID_STEPS` to its coroutine. They used to be restated inside the parallel executor while the single-step path carried its own `if/elif` chain, so `burn_pycaps_subtitles` was wired into the graph, accepted by the CLI's validity check, and silently no-op on `--step` — then recorded as done, because `_update_state_after_step` runs whether or not anything executed. A new step needs an entry in both maps plus `VALID_STEPS` in `state.py`, which is what `resolved_step_order` walks to build the graph and what the CLI accepts as `--step` choices; `tests/video/test_step_orchestration.py` fails if `step_runners()` and `VALID_STEPS` disagree, or if a step is declared before something it depends on. `pipeline_graph.py` used to carry a third declaration in `create_video_pipeline_graph`, reachable only from its own tests, which asserted a shape the producer had not run since `generate_description` was added.
- **`pipeline_state.json` is product-level while several artifacts are profile-level, so verification compares recorded paths against this run's.** A recorded artifact that exists is not necessarily this run's: rendering one product under a second profile finds the first profile's video recorded, present, and wrong. Skipping on it took the whole pipeline with it and returned a video path nothing had written, which `global_batch` counts as a success and hands to the publish phase. `_artifact_invalid_reason` rejects a recorded path that differs from `ctx.run_paths[key]`, which is why every profile-scoped artifact must be registered under a run-paths key. Until this was checked, the state was saved by an unrelated bug: `generate_description` recorded a file nothing writes, so verification failed early on every run and the pipeline never reached the point of trusting a stale entry.
- **Re-running a step drops the recorded steps that read its output** (`_drop_dependents`). `--step assemble_video` used to leave `burn_pycaps_subtitles` marked done over a video whose captions had just been re-rendered away, and the next full run skipped the burn and reported an uncaptioned video as complete. The dependents come from `data_dependencies`, not `step_dependencies`: the graph carries two edges that order execution without moving data (`generate_script` after `gather_visuals` on the scraped order, and `gather_visuals` inside the paid steps' prerequisites on the script-first one), and treating those as data made `--step gather_visuals` delete the script, the voiceover and the platform captions. Scheduling reads `step_dependencies`; correctness — what a `--step` run needs, and what a re-run invalidates — reads `data_dependencies`. Both are in `orchestration`, imported lazily because `orchestration` imports `state`. It also routes them through `_discard_stale_artifacts`: dropping the state alone is not enough, because `generate_description` and `create_voiceover` short-circuit on their own output files, so `--step generate_script` would otherwise leave the superseded script's captions and narration in the render while reporting every step complete.
- **A step that produces nothing must not be recorded as done, and an artifact recorded conditionally is how it happens.** `_update_state_after_step` registered every subtitle artifact behind an `if ... .exists()`, so a `generate_subtitles` run that wrote none of them was recorded complete with an empty artifact set -- and verification compares *recorded* paths, so an empty set is vacuously satisfied, the step is never dropped, and the run reaches an assembler with no captions (#396). The conditional recording is still right, because which artifact exists depends on the engine and on two-part mode; what was missing is that producing *none* of them is a failure. `_require_subtitle_artifact` runs at the step's top level, after the branch that chooses how captions are made -- inside either branch it cannot see the other, and `tests/video/test_subtitle_step_requires_output.py` reads the call site for exactly that, since the tests drive the helper directly and deleting the call leaves them green. Recording an empty set now warns rather than raising, because a state recorder is the wrong place to decide a run failed and subtitles can legitimately be disabled -- and the two paths that legitimately record nothing mark themselves -- `captions: "disabled"` when subtitles are switched off, `"engine_unavailable"` under `warn_and_skip` with pycaps absent -- so `_load_pipeline_state` can treat an entry with neither artifacts nor a reason as invalid instead of skipping it forever. **The marker goes at the top level of `ctx.state`, not into the step's own entry**: `_update_state_after_step` replaces that entry wholesale, so a key written into it is discarded before the state is saved, and it has to be copied through beside `script_template` and `tts_metadata` the way every other per-step scalar is. Missing that turns a supported config into a resume that truncates at this step every time, re-running the music chain and a full assembly and never converging -- and a test that hand-writes the state JSON cannot see it, because it never drives the writer. Without that reader-side half the fix does nothing for the product directory the issue was filed from, whose state file already says done with an empty set.
- **On the pycaps engine, existence is not enough: the transcript has to be the one this run wrote.** `create_unified_subtitles` returned `output_path` on `exists()` alone, and the transcript's path is stable across runs while `temp/` survives a failed one, so a timed-out transcription returned the *previous* run's transcript, the step reported success, and `step_burn_pycaps_subtitles` drew captions written for a script that may no longer be the one narrated -- worse because `whisper_transcript_file` is not in `_RERUN_BLOCKING_ARTIFACTS` while `voiceover_file` is, so a `--step generate_script` re-run drops the voiceover and keeps the transcript. The flag recording that Whisper wrote it is captured **before the Google STT block**, since Google can set `stt_timings` without writing a transcript pycaps could read, and it is a property of **the file, not of the request**: `save_whisper_transcript` is wrapped in a bare `except` upstream, so a transcription can succeed while the write fails on a full or read-only filesystem, and asking whether a transcript path was requested accepts the stale file in exactly that case. The mtime is read before the call and compared after. This is the bundled default engine, so a guard that skips this arm closes nothing.
- **`pipeline_state.json` is not only step entries, so anything scanning it must skip non-dict values.** It also holds top-level strings (`script_template`, `hook_headline`, `cold_open_variant`, `subtitle_engine_resolved`). Calling `.get` on one raises, and the resume path caught that under a broad handler that logs "Could not load existing pipeline state" — which reads as a missing or corrupt file, not as a bug. The steps did not re-run: `PipelineGraph.execute_step` checks `ctx.state` itself, and `_load_pipeline_state` already skipped non-dict values. What was lost is `load_artifacts_for_step`, which the parallel executor runs only for the steps it knows are complete — so `ctx.script`, `ctx.description`, `ctx.voiceover_duration` and `ctx.scraped_images`/`scraped_videos`/`stock_media` were all empty on a resume. Most consumers re-read their own files, but `TwoPartSubtitleHandler.calculate_visual_bounds` falls back to globbing `run_root/images` when `ctx.scraped_images` is empty, and that handler supplies the caption geometry for both the two-part upper subtitle and the pycaps burn. `completed_steps_from_state` is the one reader.
- **`PipelineGraph` catches everything a step raises and reports it as a failed step, which is wrong for a signal.** A media rejection means the product is skipped, not that a step broke, and flattening it here made `create_video_for_product`'s `InsufficientMediaError` handler unreachable from the parallel executor for several releases — the sequential `--step` path calls the step directly and always reached it: an under-mediaed product was reported as a failed render naming `gather_visuals`, which had worked. The graph now takes `propagate=(...)` — exception types that reach the caller unchanged — and the producer passes `InsufficientMediaError`. **There are two swallow sites**: `execute_step`'s `except Exception`, and `execute_level`, where `asyncio.gather(return_exceptions=True)` turns a raise back into a value; fixing only the first leaves any step that shares a level still flattened. Anything else that needs to signal rather than fail has to be declared the same way.
- **A stock-only profile needs `stock_image_count` at or above `min_images_if_no_video` (5).** Below it, `validate_media_requirements` reports the run SKIPPED rather than failed, which reads as a missing product instead of a misconfigured profile.
- **Stock search terms are concatenated into one query string** (`" ".join(keywords)` in `src/video/stock_media.py`). Every term added narrows the search, so a profile that inherits the global product-oriented defaults and adds topic words matches neither. A stock profile for non-product content should declare `stock_media_keywords: []` explicitly; omitting the key inherits the globals.
- **`VideoProfile` forbids unknown keys** (`extra="forbid"`, `visual_models.py`). A typo or a field belonging to another settings model now fails at config load rather than being dropped. The legacy flat subtitle keys are refused: the `mode="before"` validator raises naming the nested field for each one, which `extra="forbid"` would also catch but only as `Extra inputs are not permitted`. `subtitle_format` is settable per profile, in the nested spelling only -- the flat one goes through the same refusal as its siblings. It used to be refused in both, because the subtitle file's extension came from the global value while the generator wrote the merged one -- SRT text into `subtitles.ass` aborts the `ass` filter, and the mirror case ships a caption-less video silently. `_get_subtitle_filename` now takes the profile **and the CLI overrides** and reads the merged format, so the path and the contents cannot disagree by either route; it falls back to the global value when given no profile, or an unknown one. The CLI half predates the profile key: `--subtitle-format srt` aborted the render on a stock install, because every runtime consumer merges with `ctx.cli_overrides` and the path did not. Anything that builds a subtitle path has to pass both -- `tests/video/test_subtitle_format_per_profile.py` reads the `get_video_run_paths` call site in `orchestration.py` for that reason, since dropping the argument there breaks nothing else.
- **Profile-level field gating** (silent-drop class of bugs): a profile-level YAML override only reaches the assembler when ALL THREE conditions hold: (1) field declared on `VideoSettings` in `src/video/config/visual_models.py`, (2) field declared as `<type> | None = Field(None, ...)` on `VideoProfile` in the same file, (3) field listed in the `_collect_overrides` field map in `src/video/config/core_models.py::get_profile_merged_settings`. Miss (1) or (3) and the override is swallowed silently — no warning, no test failure. Missing (2) is now loud: `VideoProfile` sets `extra="forbid"`, so a key it does not declare fails at config load. When adding a new profile-overridable field, grep both files for similar fields (e.g., `image_top_position_percent`) and follow the pattern. **A fourth condition the rule does not name: something must read the target.** All three can hold and the override still go nowhere. `video_transition_duration` was mapped onto itself, and the assembler reads `transition_duration_sec` -- four profiles set a crossfade that did nothing, hidden because both default to 0.5. `tests/video/test_profile_override_coverage.py` derives the whole audit from the models and the map rather than listing fields, so it does not go stale. **That three-condition rule is for `VideoSettings` fields only.** A field owned by a different settings model (`MediaSettings`, for instance) has no slot in the `_collect_overrides` map, which targets `VideoSettings`; adding it there files a media field under video settings. Declare it on `VideoProfile` next to its siblings and have the consumer prefer the profile value, the way `use_scraped_images` and `stock_image_count` already work. Audit follow-up tracked as a GitHub issue with the `follow-up` label.
- **Subtitle config model**: `SubtitleSettings` (in `src/video/config/subtitle_models.py`) is the single source of truth — both the config-layer merge output and runtime generator input. Strict (`extra="forbid"`); YAML typos throw at load. `from_legacy_dict()` translates renames (`max_subtitle_duration` → `max_duration`, `min_subtitle_duration` → `min_duration`) and drops underscore-prefixed runtime side-channel keys.
- **Subtitle profile overrides**: `VideoProfile.subtitle_settings: PartialSubtitleSettings | None` is a single nested block; `partial.merge_into(base)` deep-merges (nested sub-models like `pycaps`, `two_part_subtitles`, `safe_zone` merge per-field). Legacy flat keys (`subtitle_anchor`, `pycaps_template`, `two_part_subtitles`, ...) are **refused**: the `@model_validator(mode="before")` shim that migrated them is gone, and the validator now raises naming the nested field for each offending key. `extra="forbid"` already catches every one of them; the validator exists for the message, which names the nested destination and lists every offending key at once instead of saying only `Extra inputs are not permitted`.
- **`crop-to-fit` returns no geometry, so it silently costs the captions their placement.** Only `letterbox` and `blur-fill` build a `VisualGeometry`; the crop branch leaves it `None` and the caller falls back to a config-based full-frame band, so content-aware captions sit over the content instead of below it. That is on top of what the crop itself costs: a 16:9 clip in a 9:16 frame keeps the centre 31% of its width, cutting the product and any on-screen text off both edges, which is why no bundled profile crops scraped product video any more. `smart-scale` is the way to reach the crop deliberately, since it only takes that branch within `smart_scale_tolerance`.
- **An explicit video top is the content's top edge, in the filter and in the geometry.** With `video_vertical_align: top`, `pad`'s y and `overlay`'s y are the literal `int(target_height * video_top_position_percent)`, and `VisualGeometry.rendered_y` reports that same row. It used to add `(scale_height - actual_h) // 2`, centring the content inside the band on paper while the frame had it flush with the band's top, so the FFmpeg engine's content-aware captions were placed `(band - content_h) // 2` too low on any profile that set an explicit top: 416px on the default 0.75 band with a 16:9 source, 656px on a full-height band. The disclosure overlay does not read the geometry, and the pycaps burn takes its bounds from the config-based `calculate_visual_bounds`, so neither moved. Nothing showed because every bundled video profile centres and the centred branch was right. The percent is read as the top edge by the filter, the geometry, the image path, the caller's config-based fallback in `visual_builder.py`, and every config-based fallback in `subtitle_builder.py` and `two_part_subtitles.py`; a change to this placement has to keep all of them in agreement, and `tests/video/test_explicit_top_geometry.py` measures the rendered frame rather than the arithmetic -- a number-only assertion would also pass if the filter were changed to centre instead.
- **The strategy factory is keyed by the values `video_assembly_mode` admits, and `tests/video/test_video_strategies.py` walks that `Literal`.** It was keyed `mixed` from v0.16.0 while the model and the bundled `product_video_mixed` profile said `mixed_media`, so every product with a video under that profile died in `assemble_video` on a `KeyError` reported as a failed render, on every release since (#372). The profile never looked dead because a product with no video takes the image-only path before the lookup. A dict lookup on a config value needs a test that reads the config's own type, not a spelling restated in the test.
- **A product image is centred in the band above the caption block, not in the frame** (#368). Neither engine puts captions at the bottom: the shipped pycaps offset places the block at 63-75% of the height and the FFmpeg engine clamps its caption to the 65% safe-zone floor, while the assembler reserved a strip at the very bottom and centred the image in the whole frame, so a tall image ran to 87% and the captions sat on it. A centred 16:9 video ends near 66%, clear of a single-line caption and a few rows into a two-line block, which is why the video profiles showed it far less. `src/video/assembler/visual_band.py` derives the caption block's top per engine -- from `pycaps.vertical_align`, `vertical_align_offset` and `caption_block_height`, or from the safe-zone floor and one styled line for FFmpeg -- and `visual_band` is the rows between the header zone (a top-aligned image starts at its `image_top_position_percent` instead, the only place that field has ever applied; `product_video_sequential` sets it to 0.45 under centring, and the first cut of this fix shrank its fill images to 269px thumbnails by honouring it) and a 2% gap above that. The assembler's image branch fits and centres inside it; the video branch is untouched. **The engine has to be the resolved one**: `step_assemble_video` reads `subtitle_engine_resolved` (re-deriving through `resolve_subtitle_engine` when a truncated state lacks it) and passes it to `set_profile_settings`, because config names pycaps on an install that burns with FFmpeg. `TwoPartSubtitleHandler._estimate_centered_image_bounds` centres in the same band, so the pre-assembly estimate and the assembler agree. `caption_block_height` is an estimate the template's CSS decides the truth of: a two-line block measured 0.105 of the frame on the bundled templates, the default is 0.12; re-measure from a frame after changing template or font size. `tests/video/test_image_band.py` reads the rendered frame's last image row, since the geometry alone would also pass if the filter were changed and the geometry left alone.
- **Video centering**: Use `video_vertical_align: center` in profile config. Setting `video_top_position_percent: 0.0` puts video at top, not center. The `center` value triggers FFmpeg's `(oh-ih)/2` pad expression.
- **Subtitle positioning**: For centered images with mixed aspect ratios (landscape + portrait), use AVERAGE `video_top` across all images to balance positioning
- **Visual bounds**: Calculated from actual image dimensions, not frame dimensions
- **Safe zone has two model homes**: `TextRenderingSettings.safe_zone` (global, `core_models.py`) and `SubtitleSettings.safe_zone` (per-profile mergeable). They reconcile one-way in `core_models.py::_build_subtitle_base` (`base["safe_zone"] = text_rendering.safe_zone`). pycaps reads the profile-merged `subtitle_settings.safe_zone`; `subtitle_builder._get_safe_zone()` must prefer the same merged value, else a profile-level safe-zone override applies to pycaps but is silently dropped on the FFmpeg burn. Defaults live in `constants.py`; `config/subtitles.yaml::text_rendering.safe_zone` restates them, so edit both or they diverge.
- **A caption must end before its successor begins, and nothing upstream guarantees that.** Every ASS dialogue line carries the same `\pos`, so two overlapping lines draw one caption on top of the other -- which reads as words drawn twice and slightly offset, and at a sentence boundary as a missing space, since the tail of one caption and the head of the next are on screen together (#389). **The overlap is manufactured here, not by Whisper**: `subtitle_timing_smoother`'s lead rule shifts every word's start 40ms earlier and deliberately leaves ends alone, so a caption appears just before it is spoken, and Whisper's own windows are contiguous -- undo the lead arithmetically on the dict artifact and 115 of 131 consecutive gaps are exactly 0.0 (the flat list gives 116, so name which artifact a count came from). **The lead is not the only source**, which is why the fix clamps the result rather than reaching back to a cause: rule 1's minimum word duration extends any word under 120ms past its successor's start with or without the lead, so a 60ms word overlaps by 60ms even at `lead_sec: 0`. The measured transcript escapes it because rule 1 extended no word of it -- state that, not a pre-lead duration, since both stored artifacts are post-smoothing and the first word's shift is truncated at zero, so its original length is unrecoverable. "The lead accounted for every overlap" is true of that render and not of the code. The lead is wanted, so the fix shortens the predecessor rather than undoing it: `_create_segments` in `unified_subtitle_generator.py` clamps a segment's end to the next segment's start. That clamp already existed on the minimum-duration path (`min(proposed_end, start_time)`); the overlap arrives on the path where the segment is long enough that the branch never runs, which is why it has to be unconditional. **The clamp only ever shortens**: assigning the successor's start instead of taking the smaller of the two reads as the same fix and is not -- it drags a caption forward through a real pause and stretches its karaoke sweep with it, since the tag durations derive from the segment's, and five of the 43 measured boundaries have such a gap -- the other two already touched exactly, because the minimum-duration branch had clamped them. Counting overlapping dialogue lines does not catch that, because an assignment produces none either. **Nor is shortening the predecessor the only way to satisfy the invariant**: delaying the successor also produces no overlaps and keeps every gap, while moving 35 of 44 captions 40ms later, which undoes the lead at each clamped boundary and is precisely what this avoids. **It is guarded on leaving a non-empty segment**: a successor starting at or before this segment did would zero the duration, and the `segment_end > current_start` check below drops such a segment outright -- losing the words is worse than the overlap being fixed. The smoother is left alone deliberately, though its gap-merge rule is guarded by `0 <= gap < gap_merge_sec` and an overlap is a *negative* gap, so it declines on exactly the input it looks like it should handle. **Neither stored Whisper artifact is pre-smoothing**, whatever `voiceover_whisper_result_raw.json` is called: `_save_whisper_debug_files` runs after both smoothing calls in `stt_functions.py`, so measuring either one and attributing what you find to Whisper is a mistake this entry made first -- `_raw` names the result-dict *shape*, not unsmoothed. The lead's fingerprint is float noise (`0.12 - 0.04` stores as `0.07999999999999999`). The two files are not interchangeable either: the dict form pycaps consumes carries rule 3's per-segment 200ms hold, which produces a 240ms segment overlap that never reaches the flat list the FFmpeg path reads, where every overlap measured 40ms. pycaps is **not** immune by construction, whatever a clean render suggests: the dict it consumes carries the same word overlaps plus that 240ms segment one, so if the symptom ever appears there, this clamp sits one layer too low to help. Verify a change by counting overlapping `Dialogue:` pairs in `temp/subtitles.ass`, checking that a boundary with a real gap kept its own end, **and** that each caption still starts on its own word -- the first two alone pass a fix that moves the wrong side. Do not verify by reading timings.

The variance across topics is larger than across models, so one script decides nothing.

- **A length floor cannot tell a description from a monologue about writing one, and the discovered free-model pool is where the monologue comes from.** `validate_description_completeness` checked non-empty, 50 characters and 10 words; chain-of-thought is *longer* and *wordier* than a description, so it cleared all three by a wide margin and one was published as a video description (#404). Measured on this pipeline's own output: real descriptions run 244-430 characters against a prompt asking for 150-300, and the chain-of-thought ones ran 1346-2686, so `description_validation.max_chars` at 900 separates them with room either side -- re-measure before moving it rather than picking a rounder number. Two structural checks sit beside it, each asserting something the prompt already demands and the monologue broke: no markdown (the real output opened `1.  **Analyze the Request:**`) and a finished last sentence (it stopped on a comma). Single-asterisk emphasis is the residual those checks deliberately miss, and it is *stripped* rather than rejected -- the repaired form is known exactly, so refusing it would spend a retry for nothing -- by `_clean_description`, the one cleaning step all four attempt paths call before validating; the guards keep multiplication, footnote markers and spaced asterisks alive, and `**bold**` stays for the validator (#409). **An emoji closes a description as well as a full stop does**, and the check has to say so: the prompt permits emoji ("no special characters except emojis") and requires no terminal punctuation, so `Grab yours today (fire)` is compliant output that a terminator-only check rejects, costing a retry on every model in the chain and, if the whole chain writes that shape, the render. Emoji-category characters are only read as a close **above U+2000**, because the same Unicode categories below it hold the degree sign and the copyright sign, and a description ending `a super wide 155` and a degree sign is truncated rather than finished. **The terminator check strips a trailing hashtag block first**, or it doubles as a hashtag rejection -- and hashtags are deliberately *not* checked, because a monologue omits them as readily as a description does, so the check would cost a retry without separating the two. It is also why the check tolerates trailing emoji: real descriptions close `power up quicker! (emoji)`. A rejected description is not fatal -- all four call sites sit inside the generation loop, so the next model or the fallback provider is tried, which is why the floors were survivable and this is worth having. **The pool is the other half.** `config/ai_services.yaml` ships `auto_select_free_model: false` at the top level but `true` inside `fallback_provider`, so the OpenRouter fallback is the path that draws unaudited models; `src/ai/model_pool.py::model_reject_reason` drops one that outputs anything besides text (the free pool carries music models, and their `output_modalities` is `["text", "audio"]`, so a filter asking merely whether text is *present* keeps them) or that reasons by default (`mandatory`, `default_enabled`, or a `default_effort` above `none` -- three spellings of the same thing in the live response, and a model declaring only `mandatory: false` is kept, since it does not reason unless asked). Unknown shapes are kept deliberately: this pool is the fallback that keeps a batch running when the primary is rate-limited, and a response shape the filter does not recognise must not empty it. **The discovery loops live once, in `model_pool.fetch_and_select_model` / `discover_any_free_model`** -- they used to exist as byte-identical copies in both generators, which is how a filter added to one was absent from the other; `tests/ai/test_model_pool_wiring.py` drives the shared functions against a crafted `/models` response and asserts both generators import them, so a private copy cannot quietly come back.

- **The Whisper timeout is derived from audio length, so it says nothing about machine speed, and a timeout is retried rather than fatal.** `_calculate_timeout` is `base_timeout_sec + audio_duration * duration_multiplier`, capped at `max_timeout_sec` (`config/ai_services.yaml::whisper_settings`). At the old 6.0 multiplier a 26.3s clip got 277.7s while the same clip measured 268.5s idle and 305.5s under load, so the margin on a healthy 16-core box was nine seconds and any contention lost the render -- late, since `generate_subtitles` runs after `generate_script` and `create_voiceover` and their cost is already spent. `make *-lowpri` makes this worse on purpose. `_timeout_schedule` in `stt_functions.py` now retries a timeout on a doubled limit (`timeout_retry_attempts`), stopping as soon as `max_timeout_sec` caps the widening, because a retry on the same limit cannot beat the attempt that just failed. **The schedule is built once and the budget shrinks as attempts run**, so `_attempt_limit` clamps each attempt again when it starts: at a 2700s budget 300s in the schedule is `[1008, 1800]`, and attempt 1 spending its whole limit leaves 1392s, so the retry's scheduled 1800 would be cancelled by the outer timeout with this step's limit unreached -- the same misattribution, on the retry path. **The reason is returned with the limit rather than recomputed**: the budget only shrinks, so a later read can only turn "the formula set this" into "the budget set this", and the message then names `pipeline_timeout_sec` for a limit raising it cannot change. That applies to the opening INFO line as much as to the error -- taking the flag from `_stt_ceiling` there while the error took it from `_attempt_limit` gave one run's log two contradictory causes for one number, and `_stt_ceiling` answers a different question anyway: "is the budget binding now", not "did the budget set this limit". With 1700s left and a 33.4s voiceover the limit is the formula's 621s and the budget is merely below `max_timeout_sec`. `_attempt_limit` is the single source; `tests/video/test_render_timeout_budgets.py` counts its callers. Only `TimeoutError` is retried: a broken model or an unreadable file fails identically twice. **The derived limit is now bounded by whatever remains of `pipeline_timeout_sec`**, because the two budgets were computed independently and the inner one could exceed the outer: at the shipped `120` and `15.0` a 59.2s voiceover earned 1008s inside a 900s pipeline, so Whisper finished inside its own budget having spent most of the run's, the pipeline timeout fired during assembly, and the log blamed the pipeline rather than the step that spent the time (#398). The crossover is a 52s voiceover, which an ordinary topic script reaches. `src/utils/pipeline_deadline.py` carries it in a `ContextVar` set by whoever applies the pipeline timeout -- `producer/cli.py` and `pipeline/phases/production.py`, both of which `tests/video/test_render_timeout_budgets.py` reads -- rather than through the four signatures between there and the STT call, which is the plumbing that already produced a documented silent failure on the subtitle engine. Reads propagate through `wait_for`, `gather`, `create_task` and `to_thread`, and are lost only through `loop.run_in_executor` -- which the Whisper subprocess uses, after the limit has been read, so it does not matter here. **Isolation between products comes from each caller setting it inside its own per-product loop, not from `wait_for`**: on 3.12 `wait_for` awaits in the current context rather than wrapping in a task, so a set performed inside it leaks back out. `create_task` and `gather` do isolate. **An unset deadline means no outer bound, not no time left**: a caller that applies no pipeline timeout must not thereby cap every step at zero, which is why `set_pipeline_deadline(0)` clears rather than expires.
- **`final_assembly_timeout_sec` is bounded the same way**, for the same reason: a flat limit larger than the time left is a promise the run cannot keep, and the outer timeout then cancels the encode with the FFmpeg limit unreached, which is the misattribution again. It never raises the configured value.
- **A killed encode must not leave a file under the finished render's name, and the partial must not be publishable either.** Both timeout attempts in #398 left a non-zero `.mp4` at the completed render's path, failing `ffprobe` with `moov atom not found`, and anything checking existence rather than validity accepts that as a finished video -- the scheduler enumerates rendered files. FFmpeg writes to `temp/<stem>.partial.mp4` and `os.replace` creates the final name only after a zero exit, so the guarantee is structural rather than a cleanup handler. **It goes in `temp/`, not beside the output**: a sibling `video_<id>_<profile>.partial.mp4` is matched by the publisher's own `video_{asin}_*.mp4` discovery glob and sorts ahead of a second profile's finished render, so a kill that skips the cleanup -- an OOM or a SIGTERM, where `finally` does not run -- would leave an unplayable file for the publisher to select and upload. `temp/` is inside the run directory, so the rename stays on one filesystem and stays atomic, and the existing temp cleanup collects anything left behind. The two caption-burn intermediates (`_pycaps.mp4`, `_ffmpeg_burn.mp4`) live there too, for the same reason (#411). **It has to be a `finally`, not an `else`**: the pipeline timeout arrives as a cancellation, so no `if not success:` branch runs at all. The suffix is preserved in the partial name because ffmpeg infers the muxer from it.
- **`pipeline_timeout_sec` and `final_assembly_timeout_sec` are sized from measured renders, and the assembly one sits inside the pipeline one, so raising either alone leaves the other binding** -- which is how the first fix attempt in #402 still lost the render. Measured on one 16-core box, idle, for a 33.4s voiceover: assembly 152s, subtitles 67s, visuals 52s, caption burn 27s, voiceover 18s, script 10s, 327s end to end. The same steps on a loaded machine with a 59s voiceover measured 671s for subtitles and 543s for assembly, so contention accounts for roughly 5.6x on transcription and 3.6x on assembly, and Whisper's cost scales with audio length against a budget that does not. **The hardware class is not what decides this**: the nominally weaker 8-core box in #402 ran several times faster per second of audio than the loaded 16-core one. The shipped 900/600 lost two renders in one day; 2700 is about 1.6x the worst run observed and 1800 is about 3.3x the worst assembly, sized for the unexplained 4.5x spread #402 records on one step rather than for its worst single figure.

- **A topic script's factual claims are checked by one grounded query after the script is written, and the check cannot lose the render** (`src/ai/script_fact_check.py`, #380). The prompt fix in 0.103.1 removed the demand that made topic scripts *invent* navigation; what a prompt rule cannot reach is a claim that is simply wrong, and a wrong menu path is followable right up to where it fails. First measured over 17 real pipeline scripts on the 2.5 tier: 83 falsifiable claims, 16 flagged, 14 right on hand review. Re-measured head to head on a fresh 17-script pool corpus for the move to the 3.x flash tier: 8 flags with 7 right against the 2.5 tier's 14 with roughly 9 -- fewer, better flags, plus two fabrications 2.5 missed outright (an invented settings path, an outdated interface claim). A false-positive share around one in eight is what every guard here is sized against. `accept_revision` is pure and refuses on the first failure, in this order: a claim spanning more than `_MAX_SPAN_PER_CLAIM` sentences, nothing returned, empty after `sanitize_script`, changed nothing, full `validate_script_completeness` including the verbatim-CTA rule, length drift, an aggregate floor (at least one body sentence of the original must survive), **containment** (a sentence neither named by a claim nor immediately following one must come back unchanged and in the same *relative order* -- not the same index, since a fix that splits a sentence shifts everything after it), then a cap of one inserted sentence per flag. The span check is first because it judges the *checker's answer* rather than the revision, and the order decides which reason is recorded, so entry and code are worth keeping in step. A refusal ships the original with the reason recorded. **`FactCheckOutcome.script` is non-optional so the bad outcome is unrepresentable**, the same governing rule the stock judge follows: a wrong sentence costs one sentence, a lost render costs the whole video and every paid step before it. **The two calls are deliberately different kinds.** The check builds its own `genai.Client` with `Tool(google_search=...)`, because `call_llm` carries no tools and should not grow them for this; the revision goes through `generate_with_llm`, **ungrounded**, because the correct fact was already handed to it and a second grounded query would double a bill of about $0.035 a script for nothing. It must be passed `secrets=`, not just `api_key`: the fallback provider looks its own key up in that dict, so omitting it makes a rate-limited primary lose the repair and ship the wrong claim while a funded fallback sits unused. There is **no round count to configure**: the module contains no loop, so the revised sentence is never re-checked -- a real gap, stated rather than hidden. A `max_rounds` field lived here briefly and was removed, because it could not raise the query count above what the code does, so it promised a second round that never happened while duplicating `enabled` at zero. A config field that cannot change behaviour is worse than none: it is read as a knob. **Grounding and `response_schema` cannot combine on 2.5** (`400 INVALID_ARGUMENT`); they do combine on the 3.x flash tier the check now runs on (re-measured: fewer, better flags, two fabrications caught that 2.5 missed, half the latency, fewer thinking tokens), but the prompt still asks for labelled lines and `parse_check_answer` tries `json.loads` first and falls back to them, so a swap back to 2.5 stays a `model:` edit. The checker prompt excludes a belief the script *attributes to others or argues against*, because the measured false positive was the checker extracting a debunked myth as the script's own claim. **Each block carries its own `RULING:` and the parser keeps only the ones ruled wrong**, because asking for wrong claims only does not hold: measured live twice, the checker listed a sentence, explained in `REASON` that it was right, and wrote `FIX: Correct.` and then `FIX: This claim is correct.` -- which spends a repair slot on a good sentence and pushes the whole rewrite past the drift guard, so the *genuinely wrong* sentences ship unrepaired. `_is_not_a_fix` is the second net and strips filler before testing, since matching the first word alone caught one of those two spellings. **Repeated claims are collapsed before the repair window** (`_dedupe_claims`, both parse paths, after the discard filters and not before -- a first copy the filters drop would otherwise take the key and shadow a genuine later correction, so the sentence ships unrepaired with nothing recorded as flagged. The filter that can do it is the raw `c.claim` truthiness check, since the key normalises the claim and the check does not: an empty claim and one that normalises to empty share a key and only the second survives. `_is_not_a_fix` cannot, being a pure function of the normalised fix, which is half the key, so equal keys always get the same answer from it; and the JSON path's verdict check sits inside the comprehension that builds the list, so it is not reorderable against the dedup at all -- a test written against it pins nothing, which is how one shipped here). A real render returned four claims that were two, each listed twice, so one of the three slots went to a repeat. It borrows the guard's normalisation but not its *relation*: the guard matches by containment either way and this by equality, so a partial quote of one sentence still takes a slot, narrower being the safe direction. The key is the claim **and** its fix, both normalised: the claim alone reads as the obvious key, since that is what containment matches on, but the prompt asks for one block per *claim* and the checker does decompose a sentence -- the one real answer available rules a single sentence in three parts -- so keying on the claim alone drops the second correction before the reviser sees it. The same answer also repeated its block set with a run-on `VERDICT:` header, which the FIX lookahead absorbed into the first copy's fix; the lookahead stops at a verdict *header* now, which is what makes first-wins safe. **It has to match the whole header** -- the word, a verdict value, and the end of the line -- and each part was added after the previous form truncated a real-shaped fix, since the fix is the only thing the revise prompt is built from and a fragment is a wrong repair rather than a missing one. The bare word cuts "the court records it as a verdict: usually within two days" at the colon; the word plus a value cuts "the scanner writes verdict: flagged into the log" at "writes"; requiring the line to end there costs nothing, because every run-on header observed ends its line. `OK` is not decoration either: the prompt specifies it as a verdict value, so a repeated answer set can begin with one. An absent ruling is kept: the block was listed under a FLAGGED verdict, and dropping it would lose a real flag to a formatting slip. The revise prompt says outright that the fix is the fact rather than wording to paste and that a longer replacement will be thrown away, because the first live repair was rejected at 38% length drift after the checker returned a paragraph per fix. **Containment matches a claim against a sentence by containment either way (`_covers`), not equality**, and sentence splitting is **one shared function**, `src/utils/script_sanitizer.py::split_sentences`, used by the containment guard, `ends_with_cta`, and the publisher's first-comment stripper: three copies of the pattern disagreed about where a sentence ends, so a repair this module confined correctly was refused by `validate_script_completeness` for not ending on a CTA -- a rewritten sentence closing on a quoted interface label merged into the CTA under the narrow pattern, and the same merge left the CTA unstripped in the YouTube first comment. It splits where sentence-final punctuation, optionally through a closing quote or bracket, is followed by a word or a quoted word -- **including a lowercase one**, deliberately. Demanding a capital stops an ellipsis or an abbreviation splitting a sentence, but it merges two real sentences whenever the second begins `iPhone`, `iOS` or `macOS`, which consumer-tech scripts produce constantly, and the two failures are not symmetric: an over-split is absorbed, since `_covers` matches a claim across the fragments and `_MAX_SPAN_PER_CLAIM` leaves room for them, while an under-split has no recovery at all -- a claim naming one merged sentence makes both rewritable, `ends_with_cta` stops seeing the closing line so the near-miss branch deletes a real sentence along with the CTA, and the publisher's stripper leaves the CTA in the first comment. The **closing-quote branch keeps the capital**, because a quotation ending in a terminator mid-sentence is followed by a lowercase continuation and splitting there published a first comment beginning "and then". `_MAX_SPAN_PER_CLAIM` is 3 rather than 2 for the same widening: one spoken sentence can carry two inner breaks (`Check the 5 p.m. reading, and then... nothing happens.`), and at 2 the checker quoting it exactly as asked lost every repair in the call -- the closing-quote half matters because a how-to quotes interface labels, so its sentences end `."`, and a lookbehind demanding the punctuation last merged such a sentence into the next one, letting one claim reach a sentence the checker never examined: splitting on the punctuation alone cut `expand Components... then read the Power page.` into two entries while the checker copies the whole sentence as the prompt demands, so equality matched neither fragment, nothing was touchable, and a correct repair was refused for altering sentences it never touched, with the record blaming the reviser. **`_covers` then has to be bounded, or one answer turns the guard off**: it matches in both directions, so a claim quoting several sentences makes all of them rewritable and a claim quoting the *whole script* protects nothing -- `_MAX_SPAN_PER_CLAIM` refuses beyond three (the bound the splitter forced, above), which still leaves room for the mismatch the helper exists for. Only one successor is added per claim, not one per sentence it spans. **That per-claim bound is not an aggregate one**, which is a separate hole: two or three claims naming *alternate* sentences, each well inside its own span, between them make every sentence of a short script touchable, and then `kept_old` holds only the closing line, every later check is vacuous, and a wholly fabricated rewrite is accepted. A revision must leave at least one body sentence of the original standing -- a script with none left is the checker rejecting it wholesale, and an ungrounded sentence-by-sentence patch is not the instrument for that. **Measured on what survived, not on what the claims permitted**: counting permission refused a correct repair of the first three sentences of five, because the fourth was touchable merely for following a flagged one and the fifth was the CTA, and the recorded reason then said the claims covered the script when they covered three of five. That is also why the floor runs after the revision is split rather than beside the span check it otherwise belongs with. Every containment test used a single claim until this was found, which is why it survived two passes. **It also checks position, not just membership**: a pure reordering kept every sentence, added nothing and held its length, so the steps of a how-to could be swapped and accepted. The position walk uses a forward cursor rather than `list.index`, which returns the first occurrence -- a script saying the same line twice, or twice after normalisation, otherwise read as re-ordered when nothing had moved. **The product arm rules against the scraped listing, ungrounded** (#383): a search is the wrong instrument for a product claim, whose ground truth is the listing already in hand, so `check_product_script` compares spec claims to `listing_evidence` (title + description; price excluded, it moves after scraping) with the same answer format -- parser, reviser and acceptance guard shared unchanged. The routing is by the record's kind, not a knob; `products` only switches the listing arm on, and `topics_only` is gone. Measured over fifteen real product scripts: two flags, both right, zero false positives. Wired as `_ensure_fact_checked` inside `step_generate_script`'s generation branch, **not** as a pipeline step (a step means `VALID_STEPS`, both dependency maps, `resolved_step_order`, artifact registration and resume truncation, four documented silent-failure classes for no gain) and **not** inside `generate_script` (five return sites, and it returns before `sanitize_script`, so a revision would be validated against text that is not what ships). After the first write, so a crash mid-revision leaves the original on disk; before `_ensure_hook_headline`, so the headline derives from the shipped text; inside the `else`, so a resume over an existing script pays nothing. `temp/script_fact_check.json` is written even on a clean verdict, so "ran and found nothing" stays distinguishable from "never ran". **It does not survive a normal run**: `orchestration` deletes the whole intermediate directory on a successful non-debug run, taking the record with the script and the gathered visuals, so re-measuring the flag rate over real renders means running them with `--debug`. Do not "fix" that by moving the record out of `temp/` -- the product directory is deleted outright after a successful publish, so a durable record needs an outputs-root file, which is a separate decision. Two negative requirements, both from documented bugs here: it is **not** registered as a step artifact (a recorded artifact that does not exist drops its step and everything after it on resume, and this file is absent on every product render), and `ctx.state["script_fact_check"]` is a **string**, because the state loader tells step entries from scalars by `isinstance(info, dict)`.

- **Stock candidates are judged from the thumbnail, over the whole pool, against the script** (`src/video/stock_relevance.py`, #341). - **Examples teach the LLM by demonstration; when examples contradict a rule, examples win**. Sibling to the body-vs-Rules gotcha above, hit on the platform caption prompts in `src/ai/prompts/{tiktok,instagram,youtube}_*.md`. - **A required rule that doesn't fit the product makes the LLM fabricate**. Phase 1.5 required analytical templates to close with a "debatable spec claim." On a passive product (phone holder, hook, organizer — no contestable numeric spec), the LLM had no spec to argue about, so it invented one and walked it back in the same sentence ("eight hours of battery life is the sweet spot for phone holders, even though this doesn't have a battery"). The class of bug is: any rule that assumes a property the product may not have will produce fabrication on the products that lack it. Fix: branch the rule on a mechanical keyword self-check ("does the description contain W, mAh, Hz, GHz, ports, hours of battery, ..."). Provide both a spec-shaped close and a fallback shape (material-or-use claim) and have the LLM pick exactly one. Anchor the rule against the actual canary case in the negative-example slot ("don't claim battery life for a phone holder"). Audit pattern: for each "always do X" rule, ask whether X assumes a property the product may not have. If yes, the rule needs a conditional branch.
- **A worked example inside a conditional branch teaches its SUBJECT, not just its shape — delete the example, don't add another warning.** The branch above still fabricated on its second outing: it produced "They say four ports is the minimum you need, but honestly, three is usually enough" for a Bluetooth tracker tag, despite already carrying the explicit "never invent a spec the product doesn't have" prohibition. The spec branch demonstrated itself with `"Most people only need two ports, but three is usually better."` and the output is that example with the numbers shuffled — the model copied the subject (ports) onto a product with none. Compounding it, the branch condition said to scan the description for tokens including "ports", and the product text had no standalone "port", only `supports` / `Portable` / `Important`; a substring scan matches all three. Fix that worked: strip the worked example from the branch that fabricates (the model must then derive the subject from the value it was told to quote), keep examples only on branches where a wrong subject is impossible (the non-numeric material-or-use branch), and make the self-check demand a verbatim quote with the unit attached as a whole word, naming the substring trap inline. Note the existing prompt test asserted the OLD rule's strings and blocked the fix — a prompt test must assert the current contract, including that the removed example is ABSENT.
- **The performance history said less than it claimed, in four ways at once, and the reports averaged over all of them.** Peak memory was the Python process's RSS, so ffmpeg, the subtitle renderer's Chromium and the STT subprocess, which is where a render's memory goes and what the OOM entries above are about, were never counted; the peak sampler was an asyncio task, so it did not run while a step blocked the loop. The trim to `max_runs` never fired, because the orchestrator builds a new history manager per render and the every-tenth-save counter restarted at zero each time (310 rows against a cap of 100). Half the rows were `--step` debug runs, many of them seconds long, recorded as if they were renders. A product skipped for insufficient media was recorded as a failure. All four are fixed in `src/utils/performance.py`: memory is the process tree sampled from a thread, the file is trimmed on every save, each row carries a `kind` and the reports read renders only, and a skip is `skipped`. A row also names its `failed_step`, since 10 of the file's 25 failures carried only "Parallel pipeline execution failed". `tests/utils/test_performance.py` pins each against the real row shapes, including rows written before `kind` existed, which are classified as renders when they recorded more than one step and reached assembly.
- **Script naturalism is a rule after the CTA rule, and on the lite model it moves little** (#438). `script_templates.naturalism.intensity` renders a rule into `{CTA_RULE}` *after* the CTA rule: before it, the rule would take the "closing beat above" referent the CTA rule points at. It offers "so", "okay", "look" and "anyway": the narrator profiles ban "honestly" and "literally", and "right" came back as a tag question on the first sentence, the one sentence the rule keeps clean. It asks for commas rather than dashes, and no "um" or "uh", because speech recognition tends to drop those and the captions would then disagree with the audio. Measured on six records per level against the same six at 0 on `gemini-2.5-flash-lite`: product scripts already carry fillers, an emotional beat and sometimes an opening "Okay, so" at 0, because the product narrator profile allows one filler; topic scripts gained about one filler; the level-2 self-correction appeared in none of six. It ships at 0, which renders the prompt byte for byte as before, and `tests/test_reach_test_holdout.py` fails if the shipped config turns it on during the reach test. Re-measure before enabling it, and expect the self-correction to need more than a sentence in the rule.
