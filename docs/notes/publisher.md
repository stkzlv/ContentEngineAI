- **Zernio (formerly Late)**: The platform rebranded from Late to Zernio. API is identical, old `getlate.dev` endpoints redirect. Our codebase still uses the old `late-sdk` package, `LATE_API_KEY` env var, and `src/publisher/late/` directory structure. Planned migration: switch to `zernio-sdk`, rename env var to `ZERNIO_API_KEY`, update imports. Both old and new SDK packages work during a 6-month grace period. No rush, but should be done eventually.
- **TikTok content disclosure**: an affiliate post **must** include `commercial_content_type: "brand_organic"` and `is_brand_organic_post: true` in `tiktokSettings`. Without these, TikTok rejects with "Commercial content disclosure is enabled but no option selected". Settings are sent both per-platform (`platformSpecificData.tiktokSettings`) and at top-level (`tiktok_settings`) in `src/publisher/late/client.py`; **both are built from `TikTokContentSettings.for_render(carries_affiliate_content)`**, so they cannot disagree. A render with no material connection declares `commercial_content_type: "none"` and `is_brand_organic_post: false` — sent explicitly, because an absent settings block is indistinguishable from a payload that forgot it. The SDK enum (`late.enums.TikTokCommercialContentType`, also exported unprefixed as `CommercialContentType` from `late.models._generated.models`) has exactly three values: `none`, `brand_organic`, `brand_content` (the last is "paid partnership"; note the spelling is not `branded_content`).
- **A non-commercial TikTok render still sends `content_preview_confirmed` and `express_consent_given`.** They look like part of the commercial-content disclosure flow, but TikTok's Content Sharing Guidelines make both unconditional requirements of the Direct Post API -- express consent before any content is sent, and a preview of the to-be-posted content -- for every post. The rejection they are easily confused with ("Commercial content disclosure is enabled but no option selected") fires only when the disclosure toggle is ON and neither option is chosen, which `commercial_content_type: none` plus `is_brand_organic_post: false` is the opposite of. Clearing them would assert that consent was not obtained and no preview shown, on a post the API requires both for. `for_render` therefore changes exactly two fields.
- **YouTube altered-or-synthetic-content disclosure is opt-in and defaults OFF** (`config/publisher.yaml::synthetic_media_disclosure`). It was unconditional on the claim that this pipeline's output qualifies on every render; YouTube's own policy page says otherwise. The bar is realistic material that could mislead about real people or events, and "production assistance ... script, thumbnail" and "cloning one's own voice to create voice overs" are listed as **not** requiring it. Nothing in the current feature set meets the bar. Two of YouTube's listed examples could apply later without any code change here — "AI generated music" and "AI generated extra footage of a real place" — since both are properties of what a music or stock provider returns, which is why the flag is gated rather than deleted. `_build_sdk_platforms` sets it at two sites (with and without per-platform content); both read `self.synthetic_media_disclosure`.
- **Caption-leading disclosure**: `PublishMetadata.format_content()` prepends `disclosure` (default `#ad`) on a line of its own, ahead of the description and hashtag block, satisfying FTC's "clear and conspicuous" placement. Case-insensitive dedup drops `#ad`/`AD`/`Ad` from the hashtag list so the disclosure never appears twice. Override the field per-render to inject language-matched variants (`#publi` for Spanish, etc.) without code changes.
- **Affiliate literal phrase is opt-in and defaults to OFF**: configured via `config/publisher.yaml::affiliate_disclosure`. When enabled, the phrase is injected into every post's caption between the `#ad` line and the description. Supports non-Amazon programs via the `program` key. The closing-frame overlay is deferred. The default is off because the phrase asserts membership of the named program, so emitting it without an active account misstates a material connection; the config loader also falls back to the dataclass defaults when the YAML section is missing **or empty**, which is why the default itself has to be off rather than only the bundled YAML. Distinct from the `#ad` disclosure in what gates it: the phrase is config-gated, while `#ad` is gated on the record carrying a material connection. Both now key off `carries_affiliate_content` (`src/scraper/base/models.py`), which returns True unless the record positively shows otherwise: a topic with no affiliate link. The producer records the decision in `metadata.json` and on each `metadata_<platform>.json`, and the publisher reads it rather than re-deriving; an absent key discloses, and a stale file is backfilled on the next render.
- **Zernio SDK gaps**: YouTube `paid_promotion` and Instagram paid-partnership tagging are NOT exposed by the SDK (verified via SDK source + Zernio docs full-text search + per-platform reference pages). Manual workaround documented in `docs/compliance.md` (per-video YouTube Studio checkbox + Instagram post-edit "Add Paid Partnership Label"). Don't bypass Zernio with direct platform APIs unless volume crosses ~5/day or analytics show real ranking impact.
- **The timeline has a retention horizon of about five weeks, and `from_date` does not widen it.** Measured live on 2026-08-23: posts aged 121, 157 and 188 days all returned rows starting 2026-07-16/17, identical with and without `from_date`; a post 248 days old returned none at all. So **day-2 and day-7 must be captured before a post ages out** — run `analytics` on a schedule, not once at the end of a comparison, because those figures cannot be recovered afterwards. Rows are lifetime-cumulative and there is **one row per platform per date**, so the timeline must be summed per date before anything reads it — taking the last row makes every figure the last-listed platform's, which is how a post that earned 1187 views stored 357. Given that reduction, a truncated read is never *wrong*, only incomplete — `views_total` stays correct while the earlier day-N figures and the ratio come back absent. `save_metrics` merges per field for that reason: taking the newer row wholesale let absence erase figures captured while they were still reachable. `timeline_end` moves with the ratio it dates, since it exists to say how mature that ratio is.
- **The scheduled sweep is installed from the repo, not by hand: `make install-analytics-timer`.** The unit is *rendered* from `deploy/*.in` because systemd forbids variable expansion in an `ExecStart` executable path and `OnCalendar` sits in a timer unit that reads no environment file, so neither the interpreter nor the schedule can be supplied at runtime. Values split by which side reads them: `analytics.limit` is behaviour and lives in `config/publisher.yaml`, while paths, schedule, timeouts and failure reporting shape the unit and live in the gitignored `deploy/schedule.env` (already covered by the `*.env` rule; its `.example` sibling commits). **The rendered `ExecStart` must never carry `--limit`** — it would be a second copy of the sweep size, so editing the YAML would change `make analytics` and not the timer, silently; `tests/publisher/test_analytics_timer_render.py` fails if it reappears. Three traps the templates encode, all of which fail silently: `TimeoutStartSec=` is mandatory because systemd disables the start timeout for `Type=oneshot`, and a hung sweep then activates forever, gets every later firing dropped, and never reaches `failed` — so `OnFailure` never fires and a stuck timer looks like a working one; `envsubst` is unusable because it renders an unset variable as empty and an empty `OnCalendar=` *resets the timer list*, giving a timer that loads, enables, lists and never fires; and the interpreter check must `import` rather than test for an executable file, since the documented failure is an interpreter that runs but cannot import the project. Verify a change to any of this with `./deploy/install-timer.sh --render-only <dir>`, which touches neither systemd nor `$HOME`.
- **Assertions about a rendered unit must anchor to the directive (`^OnFailure=`), not the bare word.** The templates carry comments explaining why a directive is absent, so an unanchored grep finds the explanation and reports the opposite of the truth. This produced two false failures while building the renderer, in both directions.
- **A day-N figure counts every platform or none.** A platform's first timeline row carries its *lifetime* total to that date, not that day's increment, and legs start reporting on their own lag. So a figure taken before a leg started counted only part of the post while `views_total` counted all of it. `views_day_2`, `views_day_7` and `durability_ratio` are now unknown when `first_report_dates` shows a leg had not reported by the cutoff — the same rule `views_at_day` already applied to an unreached window: unknown, not a small number. Measured 2026-08-25 over 60 posts, a third of day-7 figures were understated this way. A stored `None` has three causes and `timeline_end` does not separate them — a post that aged past the retention horizon before its first sweep looks identical to one with a silent leg. `lagged_cutoff_days` on the record names the cutoffs a leg was silent for. **The marker exists because the sweep that stores a figure usually cannot see the lag**: a daily run measures a young post while the slow platform has no rows at all, stores a one-leg figure that looks complete, and the per-field merge would keep it forever. This is the one case where an absence beats a stored number, so `_withdraw_lagged` runs on the merged row, not just the fresh one, and the marker is unioned across sweeps rather than taken from the newest. A sweep whose rows all begin late is truncation, not lag — legs have to *disagree* for the cutoff to be marked, and the marking sweep's record must still reach back to publication, or a leg merely absent from the oldest retained date would withdraw a ratio measured correctly while the record was whole. The same reasoning keeps a ratio taken from a full record over one computed from a truncated window: the truncated one divides by a partial `within` and reads higher, so it is a different quantity rather than a newer reading. `covers_publication` on the record is what both decisions consult, and it is `bool | None`: a row written before it existed reads as *whole*, because defaulting to False would tell the merge every stored ratio came from a truncated record and the first sweep after the upgrade would overwrite all of them. It follows the ratio that survived rather than being unioned — a union let a young sweep carrying no ratio mark the row whole, freezing the first truncated ratio permanently. **Marking and withholding are different questions**: marking is persisted and withdraws figures other sweeps stored, so it needs a record reaching publication; withholding governs only the current reading and applies wherever the retained window covers the cutoff. Conflating them let a truncated sweep store a one-leg figure unmarked. `load_metrics` filters unknown keys, like `load_registry`, or a file written by a newer release is unreadable to an older one — which then refuses to write and strands the whole history.
- **Day-N is clocked from `platforms[*].publishedAt`, not `scheduledFor`.** A leg that failed and was retried goes live after its slot, so the slot starts the clock before the video existed. `LatePublisher.list_posts` had dropped the per-leg publish time from its normalized dict, so nothing downstream could have used it; it now carries `publishedAt` per leg and `analytics.publish_time()` takes the earliest.
- **The scheduler's per-post timeline is cumulative, not daily deltas.** Each row carries total views as of that date, so a day-N figure is a lookup against one call, not a sum. Reading it as a delta understates every figure after the first row. `src/publisher/analytics.py` owns this.
- **The rich analytics calls are not on `client.analytics`.** That resource exposes four methods; `get_post_timeline`, `get_content_decay` and the per-platform calls live on `late.resources._generated.analytics.AnalyticsResource`, which the client never attaches. `analytics.timeline_resource()` is the one place that reaches into it, so an SDK release that wires them up is a one-line change.
- **The registry's content-format arm comes from the record's `topic` field, not the profile or the publish date.** A profile is a visual treatment two arms can share, and a date cannot reconstruct an arm that was interleaved, which is the only fair way to run a format comparison. `registry --summary` counts per arm and reports pre-existing rows as `unlabelled` rather than folding them into either side.
- **The registry CSV header is derived from `fields(RegistryEntry)`.** `csv.DictWriter` raises on a key its header does not name, so a restated literal list turns adding a field into a failed registry write rather than a missing column. Don't restate it.
- **The registry does not carry a pillar column, deliberately.** It had one for several releases and nothing ever read it: `registry --summary` segments by `content_format`, and no report, analytics call or tool touched `pillar`. Removing it took the producer-side plumbing with it — the pillar is no longer written into `metadata.json` or the per-platform metadata files. It is still recorded in `pipeline_state.json`, which is load-bearing for a resume, and it still shapes the script template pool, the prompt preamble and the audience. **`load_registry` filters unknown keys before constructing each row.** Every row written before a column is dropped still carries its key, and a bare `RegistryEntry(**row)` raises on all of them; the caller treats an unreadable registry as an empty one and rewrites the file, so a strict load replaces the whole publish history with the single row being added. Any future column removal depends on that filter.
- **Fixing failed TikTok posts**: Use Zernio SDK `posts.aupdate()` to set correct `tiktokSettings` per-platform, then the platform status resets from `failed` → `pending` and auto-publishes. No need to call `retry()` — the update triggers re-publish automatically. Calling `retry()` after that gives 409 "Post is currently publishing".
- **Fixing failed Instagram legs (`instagram container error: ERROR`)**: distinct from the TikTok fix above. This is a transient IG Graph container failure (`errorCategory: platform_rejected`, no `platformPostId`), not a settings problem — when YouTube/TikTok got the same media fine, the file is almost always OK. Use `posts.retry(post_id)` (NOT `update()`, which is for payload changes like the TikTok disclosure case): it flips the failed leg `failed` → `processing` and auto-republishes, leaving already-published platforms untouched (no duplicates). No re-render needed — Zernio keeps the upload on its own CDN (`media.zernio.com`), independent of Vercel Blob retention, so the media survives even after the product dir + blob are cleaned up. Resolves to `published` in ~1 min; poll `posts.get`. The `verify-delivery` command sweeps recent posts and WARNs on any `partial`/`failed` one with its failing platform and error, so a silently-dropped leg stops being invisible (`src/publisher/partial_post_sweep.py::sweep_partial_posts` is the reusable check).
- **Zernio SDK post methods**: `create`, `get`, `update`, `delete`, `retry`, `list` (+ async variants `acreate`, etc.)
- **SDK returns Pydantic enums, not strings**: `accounts.list()` returns `SocialAccount` objects with `platform` as a `Platform5` enum. Downstream code (`cli.py`, `batch.py`, `global_batch.py`, `schedule.py`) treats `acc["platform"]` as a lowercase string. Normalize in `get_accounts()` by unwrapping to `.value` before returning the dict, otherwise `.lower()` or direct string comparison fails with `AttributeError`.
- **Publishing modes**: Unified (default) = 1 post to all platforms; platform-specific (`--platform-specific` or `use_platform_specific_content: true`) = 1 post per platform with optimized metadata. Shared helper: `src/publisher/publish_modes.py`.
- **Config loading gotcha**: `publisher.yaml` may contain keys not in `PublisherConfig` dataclass (e.g. deprecated `backoff_multiplier`). The config loader in `src/publisher/config.py` strips unknown keys before constructing `PublisherConfig(**config_dict)`.
- **`.env` file**: Auto-loaded by the CLI via `load_dotenv()`. No manual sourcing needed.
- **CLI format**: `poetry run python -m src.publisher.late single <PRODUCT_ID> --debug`. Takes product ID (not file paths). Video is auto-discovered from `outputs/<product_id>/`. Don't pass `--immediate` or `--platform-specific` by default.
- **Shared link-in-bio post-publish hook**: `update_link_in_bio_safe()` in `src/publisher/link_in_bio/manager.py` is the single post-publish hook for all four publish paths (single, schedule, batch, global batch). Never raises — failures only WARN. Defaults to an enabled config. Pass `LinkInBioConfig(enabled=False)` to skip. Every new publish path should call this hook.
- **Three post-publish hooks, and the call site is the guard for each.** `update_link_in_bio_safe`, `run_blob_retention` and `run_delivery_sweep` (`src/publisher/partial_post_sweep.py`) all run after a publish and never raise. The scheduled branch of `schedule auto` had no blob-retention call for several releases while the docs listed it on every path, and nothing noticed because no test read that call site; `tests/publisher/test_delivery_sweep_hook.py` walks the AST of all four publish functions for both hooks. The sweep is deliberately not gated on `successful > 0`: the post this run created is still pending, and the value is in the previous runs' posts.
- **Registry writes are protected by `.bak` files**: `save_registry()` renames each existing `published_products.json` / `published_products.csv` to `<name>.bak` before writing the new copy. `rebuild_registry()` merges scanned entries into the existing registry instead of replacing it, so rows whose product directories were cleaned up after publishing stay in the registry. Restore from `.bak` if a write needs to be reverted.
- **`record_publish` writes are isolated per platform**: the publish-record loop in `cli.py::_record_publish_results` wraps each `record_publish` call in `try/except OSError` and logs the failure, so a tracking write that fails for one platform doesn't drop the others or surface as a publish error after Zernio already accepted the post. `outputs_dir` is resolved to an absolute path at `cmd_single` entry so anything that changes cwd downstream can't redirect tracking writes.
- **Title and description are clamped before publish, against every platform the caption reaches and on the string that is actually sent.** `PublishMetadata.clamp_for_platforms(platforms)` trims on a word boundary with an ellipsis; `clamp_to_limits()` is the one-platform spelling and delegates to it. Called from both `_publish_unified` and `_publish_platform_specific`. **The call must stay ahead of `_build_platform_contents_with_comments`**, which copies `metadata.title` into the per-platform payload: clamping afterwards would leave the copy unclamped and YouTube rejects an over-cap title. Scraped Amazon titles routinely run past 100 chars (190+ is common), so this is the normal path, not an edge case. **Two things it gets right that clamping to one platform's `description` cap does not** (#403). *The platform*: unified publishing sends one caption everywhere, so the binding cap is the minimum across the targets, and the old code took `PLATFORM_LIMITS[self.platform]` where `self.platform` was whichever metadata file `_publish_unified` found first -- the bundled order is `youtube, tiktok, instagram`, so captions were clamped to YouTube's 5000 and posted to Instagram's 2200. The refusal is total (`Failed to create post on all platforms`), so a caption too long for the tightest platform loses the post on the platforms it would have fitted too; four of five topic publishes were lost this way. The title has the mirror problem, since only YouTube declares a title cap and a first-loaded TikTok file therefore clamped nothing. *The quantity*: what is sent is `format_content()` -- disclosure line, affiliate phrase, description, hashtag block, blank lines between -- so a description clamped to exactly 2200 still composes past it. The budget is the cap less that wrapper, and the wrapper does not depend on the description, so one pass suffices. Fixing the platform without the quantity leaves posts failing by the width of the disclosure and hashtags. `_target_platforms` resolves the publish specs to enum members and drops unknown names with a warning rather than raising, falling back to `[metadata.platform]` when nothing resolves, so an unrecognised target cannot leave a caption unclamped. **There are four caption builders, not two**, and the other two were each wrong in their own way: the schedule builder (now `metadata_from_file`) never clamped at all -- a comment in the file had recorded that gap for several releases while the unified path was busy clamping against the wrong platform -- and `batch.py`'s immediate loop clamped through `clamp_to_limits`, which reads `metadata.platform` rather than the platform the loop is posting to. Both now name their destination. **The scheduling path was collapsed after four review rounds of the same defect** (#408): `metadata_from_file` returns the unclamped `PublishMetadata` -- repairing a record the model refuses (empty description, YouTube entry with no title) rather than bypassing it, since the old hand-assembled bypass returned above the clamp -- and each posting branch clamps at its own point of use with its own target list in scope: the per-platform branch `clamped_for([platform])`, the unified branch `clamped_for(<every target>)`. Those branches are `_post_per_platform` and `_post_unified` since the 744-line `auto_schedule` was split (#449), which is also why a test now fails if any method in that file passes 150 lines of code: the defect survived four review rounds because nobody could read the function it hid in. `clamped_for` is the *pure* clamp (a copy via `dataclasses.replace`; `clamp_for_platforms` still mutates for its existing callers), because one metadata object serves both uses and a mutating clamp would hand the second use the first one's narrower budget. The `targets` parameter, the `metas_used` side record and the two source-reading tests that pinned them are gone with the defect class; the wiring rule that remains is that no `format_content()` in the scheduler is legal except on a `clamped_for(...)` result, which `tests/publisher/test_caption_clamped_on_every_path.py` enforces structurally, beside behavioural tests of the budgets and the purity. The collapse also fixed two riders: the unified scheduled post now carries first comments (its per-platform payload used to copy only content and title), and the bare-literal fallback for a product with nothing on disk is routed through the builder, so it is recorded and clamped like every other branch -- but it neither discloses nor votes in `carries_affiliate`, since with no record a forced material connection would stamp a false brand-organic declaration on a unified topic post. `tests/publisher/test_caption_clamped_on_every_path.py` also asserts `clamp_to_limits` appears in none of `schedule.py`, `batch.py` or `publish_modes.py`, since that spelling is the one that silently targets the wrong platform.
- **The per-platform payload does not depend on a first comment existing.** It used to: a platform with no comment got no entry, and a run where none was generated returned `None`, so the caller skipped per-platform contents and no YouTube title was sent — the platform then derived one from the caption, whose first line is `#ad`. That is #195's sibling, which #195 described but did not close. Title and content now come from the metadata and the comment is attached when there is one. `_build_sdk_platforms` **raises** on a YouTube leg with no title rather than publishing: the provider refuses `update_post_metadata` on a pending post (`Can only update metadata on posts with "published" status`), so a wrong title cannot be corrected between scheduling and going live.
- **`schedule` enumerates products, not video files.** A product rendered under a second profile keeps both renders, and taking each of them scheduled the same product twice, on different days, burning two slots. The three batch-side discoverers — `schedule`, the immediate batch and its retry queue — share `sole_render_for_product`; `single` resolves the same render through `select_video_for_platform`, which `sole_render_for_product` calls. The two are not interchangeable: on a directory holding only a legacy-named `video_<profile>.mp4`, the shared resolver falls back and finds it while `single` does not. The immediate path uploads once per product and posts that file to each platform, so with two platforms naming different profiles only the first wins — it warns rather than routing silently. The profile has to be *plumbed in*: the scanner takes the loaded config and `BatchPublisher` takes `profiles=`, and reading it off the args namespace or the publisher object silently yields `None`, which is the alphabetically-first render again.
- **`platform_contents` entries are the authoritative per-platform payload, not a comment side-channel.** `_build_platform_contents_with_comments` builds them and `LatePublisher._build_sdk_platforms` reads `content` and `title` back out of the same dict. A partial entry is silently destructive: a missing `content` blanked `customContent`, and a missing `title` meant no YouTube title was sent at all, so the platform derived one from the caption's first line, which the `#ad` disclosure leads. Add every field the consumer reads when adding a key to either side. Hashtag-count violations stay WARN — auto-fixing them would invent or drop tags.
- **YouTube rejects descriptions with literal `<` / `>` characters**: YouTube returns `Video description is invalid` when the caption contains unescaped angle brackets (e.g., a product claim like `<10ms UPS`). The unified caption is used as the YouTube description, so any `<` or `>` from the script/description must be sanitized before publish (e.g., rewrite `<10ms` as `sub-10ms`). To fix an already-failed post, `posts.update(post_id, content=sanitized)` the unified content and then `posts.retry(post_id)`.
- **The two tracking files answer different questions; only `publish_history.json` backs the duplicate guard.** `publish_history.json` is `{"posts": {"<ASIN>:<platform>": {...}}}` — one entry per product/platform pair, keyed by the **compound** `product_id:platform` string. `is_already_published` (`src/publisher/tracking.py`) looks up exactly that key, so it is the file that decides whether `single` / `schedule` skip a product. `published_products.json` is a flat list of product rows (`product_id`, `title`, `url`, `affiliate_url`, `content_format`) with **no publish fields at all** — it records what was produced, not what went live, and the production phase writes a row even on a `--skip-publish` batch. Two consequences: a registry row alone never blocks a publish, and any script that probes history with a bare ASIN (`posts.get("B0...")`) always misses, because the key needs the `:platform` suffix. Verifying "was this published" from the bare ASIN is a silent false negative — use the compound key, or Zernio.
- **Force-republish overwrites the tracking row, losing the previous post_id.** `record_publish` writes `posts["<ASIN>:<platform>"]` unconditionally, so a `single --force` on an already-published product replaces the old `post_id` with the new one while BOTH posts stay live on Zernio. Local history then shows only the newest. To find the older post, scan Zernio (`GET /api/v1/posts?page=N&limit=50`) for the ASIN in `content` rather than trusting local state.
- **Local tracking can drift from Zernio in both directions; reconcile against Zernio, not against the other local file.** Observed on a real audit: two `publish_history` entries pointed at post_ids that return HTTP 404 `post_not_found` (posts deleted on Zernio, local row kept, so those products stay blocked from republishing), and one product live on all three platforms was absent from both local files (so `single` would have cheerfully created a duplicate). Neither direction is detectable by diffing the two local files against each other — only a Zernio sweep finds them.
- **`verify_publication` waits only while a status is transient AND the verdict is still open, and it had no loop at all before.** A platform reporting `publishing` has not finished and has not failed, so `src/publisher/cleanup.py` re-reads it on a widening delay until every leg is final or `cleanup.settle_timeout_sec` is spent. Nothing transient means no sleep and no extra API call, which is why a post read as `scheduled` (from `schedule.json`, not from `publish_history.json` -- `record_publish` writes no `status` key, so a `single` leg is always read from the API) pays nothing. Waiting also stops once the answer is fixed: one failed leg sinks a `require_all_platforms` run and one published leg carries a run that does not require all, and without that guard a `cleanup --all` sweep spent the whole budget per product to reach a verdict it had on the first read. A dry run never waits. The defect this fixes looked like a too-tight retry loop in the log -- three status reads inside one second -- but that was one read per platform: the call checked once and gave up, so on an `--immediate` publish every leg read `publishing` and the directory survived a product that went live a minute later. **Neither settle field raises on a bad value, deliberately**: `_parse_schedule_and_cleanup_config` catches `ValueError` and falls back to a default `CleanupConfig`. `enabled` and `archive_before_delete` are carried across that fallback, so a typo in a wait no longer deletes the directory on an install that had cleanup off -- everything else in the section is still lost, `keep_published_days` included, which turns a grace period into an immediate delete. Validate such fields where they are consumed. Both fields also need adding to that function's explicit key list; the parser filters the YAML section against it, so a field on the dataclass alone is dropped in silence.
- **`publish_history.json` `published_at` is queue time, not actual publish time**: The field is written when `client.posts.create()` succeeds, i.e. when Zernio accepts the post into its scheduler. The video is still queued and won't go live until `scheduledFor`. To answer "is this video actually live yet", query Zernio directly via `client.posts.get(post_id)`. Sorting `publish_history.json` by `published_at` to find "the latest live videos" is wrong: it gives you the latest-queued, not the latest-published.
- **Reading Zernio post status**: `client.posts.get(pid)` returns a `PostGetResponse` whose payload is nested under `.post` (Pydantic alias). Dump with `resp.model_dump(by_alias=True, mode="json")["post"]`. Without `by_alias=True`, every aliased field comes back as `None` and you get a misleading "no status / no scheduled_for" reading. Per-platform `status` values: `pending`, `published`, `failed`, `partial`. Real publish time is `platforms[*].publishedAt` (camelCase, only set once the platform actually publishes).
- **Empty-string `platformPostUrl` breaks the SDK's strict URL model**: a published TikTok leg often returns `platformPostUrl: ""` (TikTok gives no URL), and `None` validates but `""` doesn't, so a raw `client.posts.list`/`get` raises (`Input should be a valid URL, input is empty`) on any page containing such a post — persistently, since a published leg keeps `""` (a `processing` leg after `posts.retry` also shows `""` but clears in ~1 min). `LatePublisher.list_posts` / `get_status` (and everything routed through them: `verify-comments`, slot-occupancy detection, blob-retention) tolerate this via `_posts_list_safe` / `_posts_get_safe`: they try the normal SDK call, and on the validation error refetch the raw response, coerce `""` -> `None` (`_coerce_empty_platform_urls`), and validate the sanitized payload. A **direct** `client.posts.list`/`get` call, or a one-off script, still hits the crash — read via the raw REST API (`GET https://zernio.com/api/v1/posts/<id>` or `?page=N&limit=50` with `Authorization: Bearer $LATE_API_KEY`) to bypass it, and check first-comment delivery via the comments inbox (`pub.get_post_comments(platformPostId, accountId)`).
- **Retrying failed/partial posts (no CLI command for it)**: there's no built-in "retry failed" subcommand. List posts via the raw paginated SDK (`pub.client.posts.list(page, limit=50)`, `model_dump(by_alias=True)`), filter to the target `scheduledFor` date and top status in `{failed, partial}`, then `pub.client.posts.retry(post_id)` per post. `retry` re-publishes only the failed leg(s) and leaves already-`published` platforms untouched (no duplicates). This is the right call for a transient `TikTok upload failed or timed out` leg too (the disclosure-settings `update()` path is only for the "no option selected" rejection). `load_dotenv()` with no args resolves the `.env` relative to the calling script's own directory, so a one-off script living outside the repo root won't find the project `.env` — pass the repo's `.env` path explicitly (`load_dotenv(REPO_ROOT / ".env")`).
- **First comments fail silently; verify via the inbox, not `posts.get`**: Zernio accepts `platformSpecificData.firstComment` (YouTube + Instagram; TikTok returns None) and reports the post `published` with no error, but the comment can fail to post on-platform. The `posts.get` response only echoes the `firstComment` input. The platform inbox is the only signal: `client.comments.get_inbox_post_comments(post_id=<platformPostId>, account_id=<accountId._id>)` returns the delivered comments, and our first comment is the only one with `from.isOwner == true` (comment text is in `message`, not `text`). The `verify-comments` CLI subcommand sweeps recent published posts and WARNs on misses; `src/publisher/comment_verify.py::verify_post_first_comments` is the reusable check. Delivery is per-account flaky (seen one platform stop posting comments for a week while still publishing videos) — re-auth the failing account in Zernio. The comment also lags the video publish, so an inline check right after publish races it; the sweep on already-live posts is the reliable path. `firstComment` works on Instagram Reels despite Zernio docs claiming feed-only.
- **`PLATFORM_LIMITS` rows in `src/publisher/models.py` must reflect each platform's hard cap, not prompt-side soft targets.** YouTube row is 5000 (description hard cap), Instagram is 2200 (caption hard cap), TikTok is 2200 (caption hard cap). If a row matches the prompt's "optimal" target instead (e.g. 150 for TikTok), every caption that exceeds the soft target trips a false-positive validation WARN at publish time. The publisher loader logs and proceeds today, but #109's open policy decision could turn validation failures into blockers — at which point a too-tight row would brick every publish. Soft targets belong in the prompt config (`caption_length_optimal`, `caption_length_seo`), where they shape LLM output but don't gate the publisher.
- **Vercel Blob is a staging area, not permanent storage**: videos >4 MB upload to the user's Blob store (`LATE_VERCEL_TOKEN`) via the SDK's `upload_large`; Zernio fetches the blob URL when the scheduled post goes live, after which the blob is dead weight. `blob_retention` in `config/publisher.yaml` (age + total-size policy) trims the store once after each publish run on all three publish paths; `src/publisher/blob_retention.py` holds the logic. Blobs referenced by posts that aren't fully `published` are never deleted (`LatePublisher.get_unpublished_media_urls()` — the normalized `list_posts` drops mediaItems, so it reads the raw paginated SDK response). Retention failures only WARN; without it the 1 GB free tier fills in months and Vercel pauses store access, breaking every >4 MB upload.
