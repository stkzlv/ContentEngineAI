- **Bundled default is pycaps; Pydantic default is ffmpeg.** `config/subtitles.yaml` sets `subtitle_settings.subtitle_engine: "pycaps"` so users running the bundled config get animated captions out of the box. The `SubtitleSettings` Pydantic field still defaults to `"ffmpeg"` for programmatic construction without YAML. Default install does NOT pull pycaps — run `poetry install --with pycaps` (+ `poetry run playwright install chromium` for the CSS renderer). Forks without the optional group fall back to FFmpeg via `pycaps.fallback_policy: "fallback_ffmpeg"` in the bundled YAML, warning once with the install command.
- **Whisper transcript is a literal drop-in**: the raw `result_w` dict from `stt_functions.py::generate_subtitles_with_whisper` is exactly pycaps' `whisper_json` format. `generate_subtitles_with_whisper(..., transcript_out_path=...)` serialises it unconditionally when set (NOT gated by `debug_mode` — pycaps production runs need the file).
- **Post-assembly burn step**: `step_burn_pycaps_subtitles` runs after `assemble_video` and short-circuits when `engine != "pycaps"`, so it's safe to always include in the pipeline graph. Uses `asyncio.to_thread` because pycaps is sync.
- **Content-aware offset formula is test-only, and it would be wrong in production**: `offset = (bounds.y + bounds.height + 0.02) - 0.95`, clamped to `[-0.9, 0]`, in `src/video/pycaps_engine/renderer.py::layout_from_visual_bounds`. `merge_layout_with_template` never reaches it: the shipped `vertical_align_offset: -0.20` takes the explicit branch, and the bounds branch is a `pass`. It would also anchor the block's *bottom* edge 2% below the image, so the block's body would sit on the image. Captions stay where the offset puts them (block at 63-75% of the frame on the shipped config); the **image** is what moves, see the visual band entry in [video.md](video.md).
- **Template selection**: deterministic md5 hash `md5(product_id + ":pycaps_template")[0:8] % len(pool)`. Empty pool falls back to `template_name`. Same pattern as font/colour/script-template selection
- **Two-part incompatibility**: when engine=pycaps, `step_generate_subtitles` warns and disables `two_part_subtitles_enabled` (now `two_part_subtitles.enabled` after nesting) for that run. Single-line only in v1. The upper URL is NOT rendered.
- **Benchmark numbers** (30s 1080x1920 portrait, 40-word transcript, CSS renderer): word-focus 0.70x realtime, hype 0.79x, minimalist 0.67x. Peak RSS ~420 MB per render. CSS is faster than pictex on production-length clips.
- **CSS renderer on Ubuntu 26.04 needs a Playwright override**: `playwright install chromium` fails with `does not support chromium on ubuntu26.04-x64` (Playwright's platform detection emits `ubuntu26.04-x64`, but the registry only ships up to `ubuntu24.04`; affects ≤1.60.0, fixed in unreleased 1.61). Force the binary-compatible 24.04 build with `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu24.04-x64`. At runtime it's set automatically for the CSS renderer on Ubuntu-like distros at version 26+ by `_ensure_playwright_chromium_platform()` in `src/video/pycaps_engine/renderer.py` — the single source of truth, covering standalone producer, batch, `make`, and tests (it runs before any Playwright launch, so the Makefile needs no env wiring). It matches Playwright's own distro set (`ubuntu`, `pop`, `neon`, `tuxedo`) and uses setdefault semantics, so an explicit env wins. Only the one-time `playwright install chromium` still needs a manual prefix. Full writeup in `docs/troubleshooting.md`.
- **The CSS renderer's display requirement no longer reproduces.** When this was recorded (0.54.0, 2026-06-19) the `css` renderer launched Chromium and then hung on every `page.screenshot` (`Timeout 30000ms exceeded`) without a usable X display, on Wayland sessions and bare headless boxes alike, independent of the Chrome build (bundled 145 and system 149 both hung). Re-measured on 2026-09-02, the same burn succeeds with no display reachable by the process, and Xvfb buys nothing (33s at 466 MB peak without, 37s at the same peak under `xvfb-run -a`). `poetry.lock` has pinned Playwright 1.58.0 since before the hang was recorded, and 1.58.0 pins Chromium revision 1208 (145), the same build the June hang was recorded on, so neither the Playwright version nor the Chromium revision moved. The browser binaries under `~/.cache/ms-playwright` were reinstalled on 2026-07-30, after the entry was written, as that same revision 1208; the reinstall is the only dated change and is unconfirmed as the cause. Keep `xvfb` installed as the fallback and reach for the wrapper only when that timeout reappears. The `pictex` renderer is browserless but **preview-only**: it drops the gaps between words, so it is not the workaround either. See `docs/troubleshooting.md`.
- **Template CSS is overridden by appending, not by forking, and the append has to come after the renderer is wired.** `subtitle_settings.pycaps.force_sentence_case` (bundled `true`) makes `_build_pipeline` call `builder.add_css_content(".word { text-transform: none; }")`, which lands after the template's own stylesheet in the cascade and so beats `word-focus`'s `text-transform: uppercase` at equal specificity. Appended CSS lives on the renderer object (`_custom_css` on both `CssSubtitleRenderer` and `PictexSubtitleRenderer`), and `with_custom_subtitle_renderer` replaces that object, so an append placed before the pictex branch is silently discarded. The same swap discards the template's own stylesheet, which `TemplateLoader` had appended to the CSS renderer, so on pictex the override is the only CSS there is; pictex is preview-only, so that costs nothing, but "appended after the template's CSS" only describes the CSS renderer. `tests/video/test_pycaps_sentence_case.py` drives `_build_pipeline` with a recording builder and asserts the call order, because a test of the helper alone cannot see where the caller put it.
- **Font randomization**: the project's `subtitle_settings.randomize_fonts` doesn't affect pycaps — templates ship their own `@font-face` in `resources/`. Custom fonts go into a template directory, not into the global font pool.
- **Font/color pools**: live in `config/subtitles.yaml` under top-level `font_pool` / `color_pool` keys, validated by `FontPoolEntry` / `ColorPoolEntry` on `VideoConfig`. To add or remove an entry, edit YAML — no Python changes needed. `FontManager` and `ColorManager` load from these pools; selection methods return string names (not enums). Old pair names (`vibrant`, `warm`, `modern`) fall back to `classic` with a warning for backwards compatibility.
- **The resolved subtitle engine is a run decision, not a config value — read `ctx.state["subtitle_engine_resolved"]`.** `step_generate_subtitles` may override the configured engine (pycaps requested, not installed, `fallback_policy: fallback_ffmpeg`). Setting a local variable is not enough, and this broke every render on a default install for several releases: `create_unified_subtitles` re-reads the engine from the settings **dict** it is handed (`subtitle_utils.py`), not from the caller's branch, so a dict still saying `pycaps` writes a Whisper transcript and no SRT/ASS however the caller branched; and `step_burn_pycaps_subtitles` recomputed the engine from merged config, so it imported the missing library after the assembler had already run without captions. **There are three dict construction sites, not two** — `two_part_subtitles.py` builds its own from the same merged settings, and that branch runs only when the engine is *not* pycaps, which is exactly what a fallback run is; six of the eleven bundled profiles enable two-part, so stamping only the two sites in `steps.py` left them writing a transcript that the existence check accepted, reporting success with no captions. The engine is therefore an explicit `engine=` argument to `create_unified_subtitles` that wins over the dict. It defaults to `None`, which falls back to the dict, so the guarantee is conventional rather than enforced: a call site that omits it reads config again and reopens this bug. Pass it. `resolve_subtitle_engine` in `steps.py` is the single resolver: the burn step calls it again when `ctx.state` carries no decision, because resume truncation drops non-step keys and trusting config there re-opens the bug on the very install the fallback exists for. Anything else that needs to know which engine ran must read the state key or call the resolver rather than re-deriving it from config.
- **`subtitle_format` and `subtitle_engine` stay two fields, deliberately.** Collapsing them into one three-valued field (`srt | ass | pycaps`) reads tidier -- pycaps ignores the format, so only three of the four cells mean anything -- but `pycaps.fallback_policy: fallback_ffmpeg` switches the engine mid-run on an install without pycaps, and a collapsed field would leave that run with no format to fall back to. The fallback would then need a hidden default, which is the shape of the silent-caption bug this module already shipped once. Decided against on those grounds; reopen only with an answer for the fallback.
- **Fallback policy**: `raise` (Pydantic default) aborts the pipeline if pycaps is unavailable or fails. `fallback_ffmpeg` (bundled YAML default in `config/subtitles.yaml`) switches to the FFmpeg subtitle engine **only for the pycaps-unavailable case**, caught early in `step_generate_subtitles` (before assembly, so the assembler burns ffmpeg captions); this is what forks without `--with pycaps` hit. `warn_and_skip` keeps the video without subtitles (not recommended). A **burn-step** failure happens after assembly, and two of the four can degrade. A pycaps **render** failure (the CSS renderer with no display being the common case) and **pycaps having gone missing** since the run that recorded the engine (which a resume reaches, because it trusts that recorded decision by design) both leave a transcript and an assembled video on disk, so `fallback_ffmpeg` burns the captions with a separate FFmpeg pass via `_burn_with_ffmpeg_fallback`, reusing the Whisper transcript rather than re-running STT. The AI-tagging adapter's `from pycaps.ai import LlmProvider` has to sit inside the same `try`, or the second case dies on the import before the handler runs. A **missing transcript** or **missing assembled video** cannot: there is nothing to build captions from, or nothing to burn them onto. Those route through `_handle_pycaps_burn_failure` via `return _handle_pycaps_burn_failure(...)` (folded return so a skip can't fall through to the video swap), where `warn_and_skip` keeps the caption-less video and `raise` and `fallback_ffmpeg` both abort. A fallback that itself fails returns False and falls through to the same abort, so it cannot become a second place a caption-less video hides.
- **Module/Batch Alignment Rule applied**: the shared render-override flags (subtitle engine/format and the pycaps trio among them) are declared once in `src/video/producer/shared_cli.py::add_shared_render_args`, and `subtitle_render_overrides` applies the subtitle set for both entry points. A NEW flag still needs the two batch-side hops beside the shared module: a `GlobalBatchConfig` field and its copy in `src/pipeline/config.py`'s loader -- the helper's `getattr(..., None)` masks a missing config attribute, which is the flag-shipped-inert class.
- **3-level merge supports nested dotted keys**: `VideoConfig.get_profile_merged_settings()` understands `subtitle_settings.pycaps.<field>` and folds them into the nested `PycapsSettings` model. The same path works in `cli_overrides` dicts.
- **Pycaps upstream is alpha (0.2.1)**: pinned in `pyproject.toml` to a specific git SHA. Upgrade deliberately. If upstream stalls, fork to `ContentEngineAI/pycaps`.
- **AI word tagging via Gemini**: `subtitle_settings.pycaps.enable_ai_tagging: true` wires `GeminiLlm` (in `src/video/pycaps_engine/gemini_llm.py`) into pycaps' `LlmProvider` singleton during `step_burn_pycaps_subtitles`. Pycaps' base `Llm.send_message` declares `model` as required but real call sites pass only `prompt`, so the adapter (and the upstream `Gpt`) defaults `model="gemini-2.5-flash"`. Adapter is lazy — `google.genai` not imported until first call. Per-segment Gemini errors are governed by `ai_tagging_on_error` (default `skip` = swallow + drop tag), distinct from `fallback_policy` (render-fatal). Built-in templates `neo-minimal` and `explosive` ship `type: ai` rules out of the box and demo the feature with no project-local template needed.
- **A template's sound effects are dropped by default in the bundled config, and that is an audio decision the tag does not otherwise let you make.** `explosive` plays a `ding` on every word tagged `highlighted`, so the tag count *is* the ding count: `ai_tag_prompt_override` asks for around 15% of the words, which is 10-17 dings in a 30-second render against the one to five the template's own instruction produced. The 15% comes from `docs/subtitle-best-practices.md` and is a **visual** highlighting figure -- nothing chose it as a rate for audio, and lowering it to quiet the render would degrade the highlighting the doc prescribes. `subtitle_settings.pycaps.mute_template_sound_effects` clears `CapsPipeline._sound_effects` in `_build_pipeline`, reached the same way the CSS append and the AI-rule rewrite are. It is the only bundled preset with any effect, so clearing all of them and filtering the tag-conditioned ones are the same thing for the shipped pool. The Pydantic default is `False` like its siblings, because a bare `PycapsSettings()` is constructed in production for a config with no `pycaps:` block. Such an install has AI tagging off *and* a default `template_pool` that excludes `explosive`, the only bundled preset shipping a sound effect, so there is nothing there to mute.
- **The AI tagging instruction is a per-rule string, so it is overridable without forking a template.** A template's `tagger_rules` of `type: ai` reach pycaps as `SemanticTagger._ai_rules`, a `{Tag: instruction}` map, and `ExternalLlmTagger` renders one line per entry into the prompt it sends. `subtitle_settings.pycaps.ai_tag_prompt_override` rewrites every entry after the template is loaded, in `_build_pipeline` beside the sentence-case and punctuation helpers. It rewrites all rules rather than one named tag, because a template may declare several and a stock instruction left on one of them tags filler under a different class. Of the bundled pool only `explosive` ships an AI rule; `word-focus` ships none, so the override is a no-op there.
