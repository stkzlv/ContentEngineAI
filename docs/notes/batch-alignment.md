# Module/Batch Alignment Rule: the cases

- **The batch reads one typed publisher config, cached, resolved from the package rather than the working directory** (`_publisher_settings` in `global_batch.py`). It used to open `config/publisher.yaml` inline at four sites with a relative path, so a run started anywhere but the repository root found no file and took hardcoded fallbacks — and one of those disagreed with the shipped YAML, defaulting `immediate_publish` to True against a `false`, which publishes on the spot instead of scheduling. Every section was also parsed again at that call site: `first_comment`, `synthetic_media_disclosure`, `affiliate_disclosure`, `link_in_bio`, `cleanup` and `blob_retention` each have their own parse there, and `tiktok_settings` was simply absent for several releases (#255) — so privacy level, comment/duet/stitch permissions and the AI-content label all fell back to the dataclass defaults on the path `make batch-lowpri` runs, while `single` and `schedule` used the YAML. Nothing logs the difference. **Sharing a parser is not the guard**: the defect was a call site that called no parser at all, so the tests read the call sites (an AST walk asserting the batch's phase calls only `create_publisher_from_config`, that the factory in `registry.py` is the one `create_publisher` call carrying the kwarg, and that no `yaml.safe_load` remains in the module) rather than trusting that a shared function exists. **The loader does not coerce, so a typed field can hold the wrong type**: it hands the YAML mapping to the dataclass unconverted, and `default_platforms` and the `privacy_settings` keys are declared as `Platform` while YAML delivers strings — `to_dict()` raised on every config read from the shipped file, invisibly to mypy, which believes the annotation. `PublisherConfig.__post_init__` converts both now. Anything else added to that dataclass with a non-scalar type needs the same treatment. Tests drive this by patching `_publisher_settings`; patching `builtins.open`, `yaml.safe_load` or `chdir` reaches nothing, and `tests/pipeline/conftest.py` clears the cache around each test so one test's config cannot decide another's. One publisher now serves both the occupancy read and the publishing, so there is no second `create_publisher` call for the assertion to distinguish.
- **Topic input is on both entry points, and the batch reaches it by a different route.** The producer builds the record from `--topic` and renders it; the batch does the same and then publishes, so the flags, their names and the comma-splitting of `--topic-keywords` live in `topic_input.specs_from_args` / `materialise_topics` rather than being restated. Five things assumed a run's input was a scraped product, and each failed differently: `cli_has_inputs` counted product ids and keywords only, so `--topic` fell through to the YAML branch and scraped every configured keyword beside it; `validate_global_batch_config` refused a topics-only run as having no inputs; `discover_products_for_batch` skips topic directories on purpose, which silently dropped every topic between the phase that wrote them and the phase that renders them, so the batch opts in with `include_topics=`; the `--clean` pattern matched an ASIN shape, so topic directories accumulated and the dry-run plan under-reported what a clean would remove; and the scraping phase itself has nothing to do, so a topic run replaces it with `_materialise_topics_phase`, reported under the same phase name so resume and the summaries are unchanged. **`materialise_topics` takes an explicit `outputs_dir`** because the batch's `--outputs-dir` is not known to the video config, and deriving the path from the config alone writes every topic somewhere the later phases never scan.
- **A batch run can carry topics and scraped products at once, and each record draws from its own profile pool.** `config/pipeline.yaml::global_batch.topics` plus `topics_per_run` give a no-flag run its topics, the way `keywords` gives it its products; without them a topic could only enter a run by being typed that day, so the repeatable path produced product renders only. The two used to be refused together because `_materialise_topics_phase` *replaced* the scraping phase; both now run and `_merge_scraping_summaries` folds them into the one summary the state holds. **Removing the refusal without splitting the pool is the trap**: `_validate_topic_profiles` narrows `profile_pool` to stock-sourced profiles on a topics-only run, and doing that on a mixed run renders the scraped products from generic footage. `topic_profile_pool` holds the topic side, and the production loop picks by `product.topic`; a fixed `--profile` that draws no stock media is refused on a mixed run, since one name cannot serve both. **A resume must read its record kinds from the saved state** (`resumed_record_kinds`), not from `config.keywords`: a resume inherits the configured keywords whatever it is resuming and the completed scraping phase already ignored them, so reading them calls every resumed topics run mixed and stops narrowing its pool. Topic selection rotates on the date (`topics_for_run`), deliberately stateless — a cursor file would have to survive `--clean` and be reconciled after a failed batch.
- **`--strict` exists on all three CLIs**: exit non-zero when a product was lost, not only when none succeeded. `PipelineSummary.exit_code(strict=...)` is the batch's; the scraper and the producer implement it separately. On the batch and the producer it counts skips as well as failures: the two are reported apart because their causes differ, but for an exit code both mean a video that was asked for and does not exist, and a misconfigured profile can lose a whole run to skips while reporting no failures at all. The end-of-run summary line has to widen with the exit rule or the two contradict each other — a run that exits 1 while logging COMPLETED SUCCESSFULLY sends an operator looking for a failure that was never recorded. The scraper has no skip outcome at all: a product dropped during media validation is not counted, so its `--strict` sees only a failed product id and a keyword that produced nothing. On the scraper it had to read a new `BatchSummary.failed_keywords`, because `BatchController._process_keywords` records no per-product result for a keyword that returns nothing or whose search raises — every `ProductResult` that arm produces has `success=True`, so a check reading `summary.failed` alone was a no-op on exactly the runs the docs use as examples.
- **The random profile-pool "all profiles" rule lives once**: `eligible_random_profiles` in `src/video/producer/utils.py`, called by `load_profile_pool`, the `global_batch.py` and `plan.py` pool builds, and `src/pipeline/config.py::validate_global_batch_config`. The last caller is still the one that governs the batch: it populates an empty `config.profile_pool`, and that populated pool is what `select_profile_for_product` selects from.
- **Two `SearchParameters` classes hold the same concept**: `src/scraper/config_models.py` (Pydantic) and `src/scraper/amazon/models.py` (dataclass extending `BaseSearchParameters`). The global batch's `scraper_filters` uses the dataclass one; its defaults can drift from the Pydantic one (the `sort_order` default did: dataclass inherited the base's `"relevance"`, Pydantic had `"relevanceblender"`). When changing a search-param default, change both or confirm which path consumes it.
- **The batch dedups at handoff, not at publish**: `_drop_already_published` runs in `_execute_handoff_phase` and removes a product `publish_history.json` records as published on every platform *this run targets*, before the render rather than after it. `_execute_publishing_phase` still publishes whatever reaches it unconditionally, so the handoff filter is the only guard the batch has — anything that bypasses handoff (or a `--force` run) re-publishes and creates a second Zernio post, with the tracking row overwritten by the new post_id while the older post stays live. Two things it deliberately does not drop: a **topic**, whose id is a pure function of its title, so dropping it once would stop the arm permanently; and any product on a `--skip-publish` run, where there is no duplicate to prevent. A run whose products were all dropped exits 0 and logs `PIPELINE COMPLETED SUCCESSFULLY` with an `Already Published (not re-rendered):` line — not a failure, since nothing was asked for that does not exist. The internal outcome is `nothing new`, but nothing prints that string.
- **Both scheduled-publish paths write the local schedule, through one function.** `single` and the batch's publishing phase each ran a slot loop, published with `schedule_time`, and recorded only `publish_history.json`; the `schedule` command's `auto_schedule` was the only writer of `outputs/state/schedule.json`, so `calendar` was blind to everything the other two queued (#485). The fix was first placed on `single` alone; review applied this rule and found the batch identical. Both now call `src/publisher/schedule.py::record_scheduled_posts` after their `record_publish` loop, with the slot index when the slot was auto-discovered and `None` when the run fell through to immediate. `tests/publisher/test_single_publish_records_schedule.py` reads all three call sites by AST; `cmd_single` and `cmd_calendar` are driven by nothing else, while the batch's auto-scheduling test in `tests/pipeline/test_global_batch_publishing.py` runs the phase for real and asserts on the file it writes.
- **The batch's publisher comes from the same factory as the CLI's.** `create_publisher_from_config` in `src/publisher/registry.py` is the one place the loaded settings are handed to the provider. The batch used to build its own publisher by hand, which is how `tiktok_settings` went missing from it for several releases, and how `timeout` and `max_retries` never reached it at all: the batch ran on the provider's defaults while `single` ran on the configured values, and nothing compared the two. `tests/publisher/test_shared_publish_helpers.py` fails if either path calls `create_publisher` directly again. The batch still takes its key from `LATE_API_KEY` at publish time and passes it to the factory, because the settings it reads before the run may carry the placeholder that stands in for an absent credential.
- **The batch's slot search is the schedule manager's.** The publishing phase read the provider's posts and walked the slots with its own loop, a third copy beside `single`'s and `ScheduleManager`'s. It now calls `build_occupancy` and `next_free_slot`, so the occupied set includes the local schedule as well as the provider's posts, the search budget is the shared constant, and a change to what counts as occupied lands on every path at once.
- **Cleanup after a publish is two policies, on purpose for now.** The batch removes the product directory as soon as every targeted platform accepted the post (`remove_published_product_dir` in `src/publisher/cleanup.py`); `single` and `schedule` go through `CleanupManager`, which checks the product's age and, by default, asks the provider whether every leg is live, which a scheduled post never is yet. The split kept the batch's behaviour and named it; which policy the batch should follow is #491.
