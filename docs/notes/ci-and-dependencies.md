- **CI installs the optional `pycaps` group, so the gated tests run there.** The test job's `poetry install --no-interaction --with pycaps` is what makes `pytest.importorskip("pycaps")` tests execute in CI, including the two in `tests/video/test_pycaps_integration.py`, both of which render through `pictex`, whose skia-python binary links `libEGL.so.1` and `libGL.so.1`: the job installs `libegl1` and `libgl1`, because the first CI run with the group failed exactly those two tests on the missing library. No test renders through the CSS renderer in CI (`playwright install` is in the job, but nothing exercises it), so a Chromium-side regression is still invisible there. The venv cache key ends in `-pycaps` for that reason: the key hashes `poetry.lock`, which does not change when a group is added to the install command, so without the suffix a cached venv from before the change would be restored without the group and the tests would skip again while the job stayed green. The missing-pycaps tests simulate absence by patching, so they run either way. A default `poetry install` still omits the group; that install's FFmpeg fallback is unchanged and is what forks get.
- **mypy error codes differ between versions.** CI installs mypy from `poetry.lock`; local dev may have a different version from `pip install` overrides. The `google` namespace package triggers `attr-defined` on mypy 1.15 but `import-untyped` on 1.19. Never use inline `# type: ignore[specific-code]` for cross-version issues. Use a module-level override in `pyproject.toml` with BOTH codes: `disable_error_code = ["import-untyped", "attr-defined"]`.
- **Run the gates after the last edit, not before it, and mind what mypy cannot see.** Two ways a green local run still fails CI, both hit in one session: gates run before a file was added say nothing about that file (a new test tripped `SIM101` in CI), and **an import moved into an `if TYPE_CHECKING:` block is invisible to mypy by construction** -- it believes the name exists, so a runtime use of it (`Path(...)` in a function body, not an annotation) is a `NameError` that only the suite catches. When moving an import there, check every use is an annotation, and remember `from __future__ import annotations` stringifies annotations but not default values, base classes, or anything read by `get_type_hints`.
- **Always run `poetry run mypy .` (whole project), not `mypy src/`.** CI runs `mypy .` which scans 267 files including tests. `mypy src/` only checks 144. The difference can hide errors.
- **Before pushing, run the exact CI commands** from `.github/workflows/ci.yml`: `poetry run ruff check .`, `poetry run ruff format --check .`, `poetry run mypy .`. Don't substitute with `make lint` or `mypy src/` — they can diverge.
- **Never pipe a gate into `tail`/`head` when chaining with `&&`.** A pipeline's exit status is the *last* command's, so `poetry run mypy . 2>&1 | tail -1 && poetry run pytest` runs pytest even when mypy failed, and the chain reports success. This has shipped a red CI twice: once hiding a `ruff format --check` failure behind an earlier "All checks passed!", once hiding two mypy errors in a new test file. **Only a bare invocation preserves the status** — `grep` is no better than `tail`, and is worse for being plausible: on a failing mypy the `error:` lines *match*, so grep exits 0 and the chain continues. Run each gate as its own command. A `grep` filter is for reading output, never for a link in an `&&` chain. `set -o pipefail`, or testing `${PIPESTATUS[0]}`, is the only safe way to pipe one.
- **`warn_unused_ignores = true`** is enabled. Bare `# type: ignore` works but module-level overrides in `pyproject.toml` are cleaner because they survive mypy version changes without unused-ignore noise.
- **Poetry explicit source pins don't cascade to transitive deps.** `torch` is pinned to `pytorch-cpu` (`source = "pytorch-cpu"`), but `torchaudio` pulled transitively by `coqui-tts` still resolves from the default PyPI index (CUDA wheel), failing at import on CPU boxes with `libcudart.so.13: cannot open shared object file`. Fix: pin `torchaudio` explicitly to the same source. Any PyTorch-ecosystem package used at runtime needs its own source entry — don't assume `torch`'s pin propagates.
- **A package you import directly must be declared, even when a dependency already drags it in.** `pillow` was imported as `PIL` by the scraper's media validator, the image utils and the subtitle sizing path, but was never in `pyproject.toml`: it arrived transitively through `coqui-tts`. Dropping that one dependency took `PIL` with it and broke the scraper at import. Nothing catches this while the donor is installed, and `poetry install` will not either, because it only adds. Use `poetry sync`, which removes what the lock no longer names, to see what a fresh environment actually gets. **But never run `poetry sync` on this install without expecting to reinstall Poetry afterwards**: Poetry lives inside the project venv it manages (`virtualenvs.create=false`), it is not a project dependency, so sync uninstalls Poetry's own packages mid-run and dies on a missing `cleo` module -- the project side completes, but `pip install poetry==<same version>` is then needed to get the CLI back. When removing a dependency, grep the source for imports of every package the lock drops, mapping distribution names to import names (`pillow` -> `PIL`) rather than matching on the distribution name alone.
- **`openai-whisper==20240930` won't build in a fresh PEP517 env.** Its legacy `setup.py` imports `pkg_resources`, which setuptools removed in `>=81`. Poetry's isolated build env always grabs the latest setuptools, so `poetry install` fails on a clean venv with `ModuleNotFoundError: No module named 'pkg_resources'`. Fix: `pip install 'setuptools>=78.1.0,<79' wheel` into the active venv, then `VIRTUALENV_SYSTEM_SITE_PACKAGES=true poetry install` (the build env then sees the venv's 78.x setuptools). `PIP_CONSTRAINT` does NOT propagate into Poetry's build subprocess. Never `pip install openai-whisper` directly to work around it — pip pulls `torch` (CUDA wheel) from PyPI over the `pytorch-cpu` source pin, Poetry then thinks the venv is satisfied and skips the CPU build; recover by recreating the venv. Full writeup in `docs/troubleshooting.md`.
- **`pytest --cov` + transitive torch.** Coverage instrumentation re-imports modules, which makes torch's `overrides.py` raise `RuntimeError("function '_has_torch_function' already has a docstring")` the second time it loads. If a module imports a torch-using package at module load (e.g. `from TTS.api import TTS`), pytest-cov sessions crash before any test runs. Fix: defer the import to first use via `importlib.util.find_spec("X")` for the availability check + a lazy `from X import Y` inside a function. Pattern is in `src/video/tts.py::_load_coqui_tts_class`. Same pattern works for any torch-transitive dependency that doesn't need to load until a feature path actually executes.
